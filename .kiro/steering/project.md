## Snowsight deliverables (BINDING, every phase — ruled 2026-09-11)

The generic rule is `reference/toolchain.md` §11; this is its application here, with the history that bought it.

- **Anything Scott is asked to run in Snowsight delivers its evidence as ONE final statement returning ONE grid**, with columns `check_name | result | detail` and `result` printing `PASS` or `FAIL` per check.
- **Multi-statement verification blocks whose results must be clicked through or exported are PROHIBITED.** Snowsight displays and exports one grid — whichever is showing. Ignoring that cost three round-trips on 2026-09-10/11:
  - a probe whose CSV export carried only its last result set;
  - a retrofit (P9) folding the rest into one grid;
  - an eleven-grid verification block that could only be read by matching comment labels to SQL.
- **Where evidence needs intermediate states** (a load, a reload, a reset), the working form is **one Snowflake Scripting block**:
  - `EXECUTE IMMEDIATE $$ … $$` performs the steps and records each check into a session-temporary table.
  - It ends with `RETURN TABLE(...)` over that table.
  - An `EXCEPTION` handler appends a FAIL row carrying the error text, so a stopped run still returns the checks that ran.
  - Every object is fully qualified, because the statement relies on the worksheet's role and warehouse, not on `USE`.
  - First instance: `snowflake/verification-summary.sql`.
- **Setup is not evidence.** A script that creates objects may run many statements; its verification is a separate one-grid statement.
- **If a deliverable genuinely cannot be one statement,** each grid-producing statement is explicitly marked `-- SCREENSHOT THIS GRID`, and their number is kept to a minimum.

## Business rules

- Reason → remediation mapping is ONE rule (`SO_remediationForReason`): the four pairs from the vocabulary canon, each with an SLA urgency. The SO Triage Agent's propose-remediation tool wraps this rule; the agent never invents remediations.
  - Verified live 2026-09-02: `insufficient_securities` returns `Arrange cover borrow / partial release` / `HIGH` / `Settled - Borrow Executed`. All four pairs and the `Manual review` fallback break-tested through `testRule`; canon and build agree.
- Priority = risk × time-to-cutoff (`SO_casePriority`), computed from FAIL_PROBABILITY and EXPECTED_SETTLEMENT_DATE. A medium-risk trade settling in 90 minutes outranks a high-risk trade settling Thursday. Drives analyst queue sort.
- Confidence gate: XOR on `confidenceScore` against constant `SO_CONFIDENCE_THRESHOLD` (demo-tunable live; changing it visibly changes the straight-through rate). Above: straight-through resolution with audit write + notification. Below: analyst task with the agent's full reasoning attached. Separate branch for clarification/escalation.
- **ESCALATION FOR A BREACHED WINDOW IS A PROCESS-LAYER POLICY, NOT AN AGENT JUDGMENT — ruled 2026-09-22.** If broker confirmation lag exceeds the hours remaining to cutoff at triage time, `SO_triageCase` escalates, **ahead of both the straight-through gate and the analyst lane**: once the window is gone, releasing and referring are both wrong. The `counterparty_default` reason override is unchanged and still escalates on reason alone. **Why it is not left to the agent:** the same case at the same score routed two different ways on two runs, because the agent's `escalate` flag is not deterministic, and a narrated beat cannot depend on a coin-flip. The score is still recorded, shown and audited — it just does not decide this lane. The breach arithmetic (lag, hours remaining, score) is composed into the escalation event from values in hand, per the fixture-prose canon, and every escalate path renders the fail reason through `SO_failReasonDisplay`, lower-cased into the sentence.
- confidenceScore semantics: the agent's confidence that the proposed remediation is the correct course of action, based on case facts. **The model's fail probability is explicitly excluded** — probability answers "will this trade fail" and is why the case exists; confidence answers "is this the right fix". Never a guarantee of execution feasibility (lending inventory, treasury balances), which is downstream desk work. **Only genuinely concerning facts lower it** — unusually large notional for the desk, a high-risk counterparty or above-average historical fail rate, a tight window; concerning facts compound. **Favorable facts are reassurance and must not lower it**, and a case favorable across the board earns 0.85 or higher. The timing arithmetic is mandatory: broker confirmation lag against hours remaining to cutoff, both numbers stated; lag at or near the remaining hours means the remediation cannot complete and the case goes to a human at confidence 0.5 or lower.
- **`SO_caseContext` shape (the agent's entire view of a case).** Six labeled lines, in this order, assembled process-side in one query — never four agent tool calls (§11: Agent Studio record-data tools do not traverse relationships):
  1. `CASE:` id, status, desk, fail reason, cutoff + **hours from now** (the denominator of the timing arithmetic)
  2. `TRADE:` trade id, instrument id, direction, **notional thousands-separated** (raw concatenation emitted `1.87005e+07` to the agent — always format), expected settlement, desk, broker confirmation lag (the numerator)
  3. `INSTRUMENT:` ticker — name | instrument id, so the agent says "SAP GY / SAP SE" rather than reciting `INS0147`
  4. `PREDICTION:` fail probability, risk tier, scored-at, predicted reason
  5. `COUNTERPARTY:` name, type, region, risk tier, historical fail rate
  6. `ONWARD DELIVERIES:` a plain statement, not a number to re-derive — either "no onward deliveries … contained to this settlement" or "N onward deliveries … a fail may cascade", from `SO_onwardDeliveries`
  **Penalty accrual is deliberately NOT in the context.** `SO_penaltyAccrual` is a screen figure — what another day costs — not a fact the agent should weigh when judging whether a remediation is the right fix. Keeping it out preserves the confidence semantics.
  **Pending a Designer re-sync**: ISIN, settlement venue (CSD), and matched status + matched time. The Snowflake columns exist; the record-type fields do not, and `addRecordTypeField` cannot map an existing external column (measured — see below).

## Repeatability (hard requirement — multi-SC asset)

- **RE-DATE THE STANDING CASES BEFORE RENDERING A PHASE 4 SCREEN: RUN `SO_redateStandingCases`.** From 2026-11-12 the re-date is a process model, not a script. **Prepare the demo runs it** (`SO_prepareRun`, between clearing the last run and loading the next), so a presenter never thinks about it. A build session that renders a Phase 4 screen on a day when Prepare has not run starts it through `testProcessModel` (no inputs) and reads `pv!message`, which starts `OK ` on success. The offsets live in ONE rule, `SO_standingCaseOffsets`; the stamps are computed by `SO_standingCaseRedate`; `fixtures/p4-verify-redate.py` and its three CSVs are superseded and kept only as the record it was verified against (same stamps for the same UTC hour, 2026-11-12). **THREE TABLES MOVE TOGETHER OR THE AUDIT TRAIL LIES:** the model writes the 17 cases, their 12 comments and their 14 events on one clock, rounded down to the hour in UTC, because the assessments and the activity timeline are stamped on the same clock as the cutoffs, and re-dating only the cases leaves the agent apparently running days after the case opened. Standing-case cutoffs are absolute timestamps and decay daily: a session that renders without re-dating shows a book entirely past cutoff and an "Inside critical window" KPI of zero, which reads as a broken screen rather than stale data. The model is idempotent — every case is pinned to an OFFSET FROM THE CLOCK, never shifted by a delta — so a second run in the same hour writes the same values. It re-dates triage stamps on the same clock, because the stored assessments quote "roughly N hours remaining to cutoff" as of triage; letting the two drift apart rebuilds the fiction defect automatically.
  - **IT WRITES BY ID AND CHECKS THE IDS FIRST.** Every write names its ids; nothing is selected by query. Before the first write the model confirms that every case, comment and event listed in `SO_standingCaseOffsets` is readable on the site, and stops with a message if one is not, because Write Records re-creates an id that no longer exists as a blank row (measured 2026-11-12, the cause of the 2026-10-22 blank cases). The check reads as the account that started it, so that account needs `SO Supervisors`.
  - **IT MOVES TIMES AND NOTHING ELSE.** A standing case that a rehearsal has changed (status, assignee, disposition, an added comment) keeps the change; the re-date does not restore it.
  - **IT WRITES NO AUDIT EVENT.** A re-date is maintenance, and maintenance that logs forges a trail of edits nobody made.
  - **THE HEADROOM RULE, learned by rendering rather than by reasoning:** the rail recomputes "does the remediation fit the window" from the LIVE clock while the assessment states the arithmetic as of triage. A case whose assessment says the remediation FITS needs `cutoff offset >= broker confirmation lag + ~3h`, or the two agree at re-date time and silently diverge within the hour — rail saying "does not fit" beside an assessment saying it fits. A case whose assessment says it does NOT fit is safe at any offset, because time only makes that verdict more true.
  - **Contrast, deliberately: the Phase 5 packet inserts cutoffs RELATIVE TO NOW at insert time, so a simulated feed never needs this.** This ritual exists only for the hand-authored verification fixtures, and it disappears when they do.
- **FIXTURE ROWS MUST BE STATES THE REAL FLOW CAN PRODUCE, AND FIXTURE PROSE IS COMPOSED FROM THE ROW, NEVER AUTHORED BESIDE IT.** Status, escalate lane, confidence, remediation and assessment presence all have to agree, and reason overrides bind — `counterparty_default` is never released, whatever it scored. A scored case has an assessment; a `New` case has neither score nor assessment. Every figure in the prose is read off the record, using the SAME rounding the screen uses (`round()`, not `text(x,"0")`, which truncates — a truncating dump had assessments saying 82% where the rail rendered 83%). A fixture whose narrative and data disagree is worse than no fixture: the screen looks alive while it lies, which is the forged-escalation failure mode with a human in the fabricating seat.
  - **A TIMESTAMPED ASSESSMENT DISAGREEING WITH THE LIVE CLOCK IS CORRECT, AND NO SESSION MAY "FIX" IT — ratified 2026-09-09.** On the past-cutoff case the agent card is stamped 06:00 and says "1.0h remaining" while the TIMING card beside it says "Past cutoff". That is not an inconsistency; it is an **audit artefact next to a live reading**, and the contrast is a governance talk-track beat: the machine's reasoning is a dated record of what it knew when it ran, and the clock kept going. Making the two agree would require either back-dating the clock or rewriting history — the second of which is exactly what an audit trail exists to prevent. Leave it. The same holds for the headroom drift below: an assessment saying "roughly 4.0 hours remaining" beside a banner reading "2h 42m" is the same artefact, correctly stamped.
  - **AND THE PROSE IS COMPOSED FROM THE ROW AS IT STOOD AT THE RUN TIMESTAMP, NOT AS IT STANDS NOW** (2026-09-09). An assessment is a dated artefact: it says what was true when the agent ran, and the screen stamps it with that time, so its arithmetic must reconcile against the run rather than against the clock. The past-cutoff fixture had been written from the *demo's* vantage — "the cutoff has now passed" — while its own run stamp sat an hour BEFORE that cutoff, and the event log written from the same moment correctly said "1.0h remaining". Two artefacts of the same instant contradicting each other, both rendered faithfully. Compose from the row at `runAt`; let the live cards say what is true now. The re-date script's `triage_offset()` guarantees the run precedes the cutoff, which is what makes this checkable at all.

- **A CASE DELETED WHILE ITS TRIAGE IS RUNNING IS NOT WRITTEN BACK — `SO_triageCase` node 14, 2026-11-12.** The agent call takes 25 to 45 seconds. Before the guard, a case deleted in that window was re-created by the first write after the agent returned: Write Records, handed a primary key that no longer exists, inserts a row under that key holding only the fields it was given. Measured on version 14.0: the row came back with a status, a remediation and a score, and no trade, session, desk or cutoff, with one comment and two events. That is the cause of the blank cases of 2026-10-22. Node 14, "Case still exists?", sits straight after the agent node and ends the process when the row is gone. **Any new write to a case by id needs the same question asked first.**
- **PREPARE THE DEMO IS ONE BUTTON, AND THE RUN IS RECORDED — 2026-11-12.** The console's button starts `SO_prepareRun`, which answers in about 5 seconds: it reads `SO_demoRunState`, refuses if a run is in progress, otherwise writes one `SO Demo Run` row (status PREPARING, who, when) and starts `SO_prepareRunSteps` in the background. That model runs `SO_resetRun`, `SO_redateStandingCases` and `SO_simulateRun` in order, stops at the first step that fails or refuses, and closes the row: LOADED, or FAILED with that step's message word for word. **Why two models and a record:** the three steps take 34 seconds in a row, a page waits 30 at most for a synchronous start, and for the first half minute of a Prepare the data holds no packet and no case, so a rule reading data alone said "Nothing loaded" and let a second press through. The record is what makes the state read Running from the press, for the process and for any page loaded after it. **`SO_demoRunState` is the one definition of the run's state** (seven values, the status line and its colour, and the last failure); the console and `SO_prepareRun` both read it. A new consumer reads the rule; it never re-derives the state. **A PAGE READS THE RULE ONCE, WHEN IT LOADS — found 2026-11-13.** The rule is built from local variables, and a rule's local variables do not re-evaluate when the page variable that calls it refreshes, `refreshAlways` or not (Appian docs, "Nested rules need refreshAlways"). So the pressing page did not show Running until it was refreshed. The page now holds its own press: from a press that started a run it shows the rule's `whenRunning` output (the Running line, tone and `isRunning`), so the sentence still has one home. **Any page value that must change after the page's own action is set by that action, never waited for from a re-read of a rule.**
- **A PROCESS-WRITTEN CASE HAS NO `createdOn` AND NO `modifiedOn`, AND A FIXTURE CASE HAS BOTH — MEASURED 2026-09-23.** All three cases written by `SO_intakeRun` / `SO_triageCase` read back NULL on both fields; all three fixture resolved cases read back populated, because `p4-verify-redate.py` writes them. **Two binding consequences.** (1) **Any screen that formats either field must guard the null**, or it takes the whole page down: `SO_supervisorCommand` line 351 calls `text(modifiedOn, …)` unguarded where line 345 guards the same field, and since every demo run produces exactly one straight-through resolution, the supervisor screen fails for the entire demo window. (2) **A process-created row's "when" is read from a field the process actually wrote** — `resolvedOn` for a resolution, or the packet prediction's `SCORED_AT` for the load time, which is what the Demo Admin console's status line uses. Never reach for an auto-managed timestamp on a row a process created. The general form — *a fixture set and a process-written set can differ in which system-managed fields are populated, so a screen verified against fixtures is not verified against production rows* — is staged for promotion, not yet portable.
- Every demo run is session-tagged (sessionId on cases, comments, audit, resolution events). Snowflake baseline data (the 50K) is never mutated by a demo run; demo-created Snowflake rows (Phase 5+ simulation, Phase 8 loop-back) carry sessionId too.
- `Reset Demo` (Demo Admins): deletes session-tagged Appian rows, cancels orphaned processes, runs the Snowflake session-row cleanup. `Verify Ready` (Demo Admins): baseline counts, zero open demo cases, MCP reachable (one cheap tool call), warehouse warm — green-checks screen.
- Feed simulation: fixed scripted packet — **15 trades: 3 seeded High/Critical stories that open cases, 12 background trades below the High floor (p < 0.5003) that do not**. Contract `packet-spec.md`; ids `TRD9 || <run name without dashes, ≤13> || 01..15`, reset by exact id list. Identify seeded specimens by properties, never platform-assigned ids (appian-supplemental §5).

## Working style

- **TOP-LEVEL LAYOUT FOR EVERY FULL-PAGE SCREEN IS `a!formLayout(contentsWidth: "FULL")`, never `a!headerContentLayout`.** MEASURED 2026-09-03: `a!headerContentLayout` has NO width parameter at all — its full signature is `(header, contents, showWhen, backgroundColor, contentsPadding, isHeaderFixed)` — so an interface built on it cannot control its own width and renders as a centred fixed-width band. `a!formLayout` is the only top-level layout with an explicit contents-width control; `contentsWidth: "FULL"` renders as `formWidth "FULL"`. Set `focusOnFirstInput: false` so the page does not steal the cursor into a filter on load; omit `titleBar` and `buttons` so no form chrome appears. **Trap:** `validateExpression` ACCEPTS `contentsWidth` on `a!headerContentLayout` with no errors — only the object validator rejects it. `validateExpression` is not a reliable keyword check.
- **A KPI BAND'S SUB-LINE MUST FIT ONE LINE, OR THE BAND GOES RAGGED.** Six tiles across a full-width form are equal height only while every sub is a single line; one caller writing a long sub silently makes its own card taller and the row uneven. Budget at 1440px is roughly **37 characters** for the narrowest card in a six-card band (one sixth of ~1400px, less card padding, at SMALL rich text) — an ESTIMATE, not a measurement, so treat it as a design ceiling and confirm in a browser. Qualifications that do not fit are not deleted: they go in `SO_kpiCard`'s `tooltip`, which composes them with the Snowflake provenance note so a marked card never loses its explanation. (Learned when a 65-character sub carrying a sampling note made card 1 taller than the other five.)
- **A FIXED-GLYPH BAR MUST OWN ITS LINE. NEVER PUT ONE IN A FLEXIBLE SLOT BETWEEN FIXED SIBLINGS.** The supervisor's reason bars were built as a `a!sideBySideLayout` of `3X` label / flexible glyphs / `3X` figures: the fixed siblings claimed their width first, the glyph run got the remainder of a MEDIUM_PLUS rail, and `preventWrapping` turned the overflow into a bar chart ending in an ellipsis. Same starvation family as the gate-A ticker beside a `MINIMIZE` sibling. **The working form is the label on its own line and the glyph run plus its figures on the next, in ONE rich text field with `char(10)` and NO `preventWrapping`** (which would collapse those paragraphs anyway). **Size the budget from a bar already proven in the same container**, not from arithmetic: the Analyst Queues card renders 14 glyphs with a 41-character trailer in that rail without truncating, so 14 glyphs with a 15-character trailer is safe by construction.
- **CARD HEIGHT: `a!cardLayout(height:)` EXISTS AND IS THE WRONG TOOL FOR ALIGNMENT.** Valid values EXTRA_SHORT / SHORT / SHORT_PLUS / MEDIUM / MEDIUM_PLUS / TALL / TALL_PLUS / EXTRA_TALL / AUTO (default). **A fixed value makes the card's contents SCROLL when they do not fit** — that is clipping with a scrollbar, and a supervisor scrolling inside a card to reach the fourth analyst queue is worse than an uneven column edge. There is **no "stretch to fill"** and **no cross-column bottom-align**: `alignVertical` positions content within a row, it does not stretch a card, and `a!cardGroupLayout(cardHeight:)` equalises cards with *each other* while inheriting the same scroll behaviour. **Balance two columns by shortening the elastic content (a chart's `height`) and by spacing, never by fixing card heights.** The residual gap is a browser measurement — chart and card heights are named enums with no documented pixel values and the render tree carries no geometry.
- **RAIL/PANEL TYPE: ONE SCALE, TWO EXCEPTIONS.** `SMALL` muted labels; `STANDARD` **semibold ink** values — every value: notional, score, lag, counterparty, settles, side. Two exceptions at `MEDIUM`: **the ticker**, and **the probability value plus the live countdown value** (in semantic colour), both short by construction so neither can wrap or truncate. Their context — the tier word, "to cutoff · 15:00" — stays STANDARD or SMALL. **Nothing else exceeds STANDARD. There is no LARGE anywhere.**
  - **THE MOCKUP CSS IS THE STRUCTURAL TYPE AUTHORITY — map to the nearest platform size, never invent a scale.** `mockups/analyst_watchlist.html` puts the whole rail inside a FOUR PIXEL range (labels 11–11.5px, values and prose 12.5–13.5px, one 15px element: `.pv-head .instid .tick`). The build's deliberate correction is *weight and colour* — the mockup's values are a thin mid-grey, ours are ink and STRONG — not size.
  - **EMPHASIS IS WEIGHT AND COLOUR, NEVER SIZE. If a render reads flat, the escalation path is weight and spacing, never a third size.**
  - **Why the rule is this blunt (measured twice):** a "key number" tier at LARGE made the rail worse three ways at once — a giant countdown chip that read as a headline rather than a status, a notional truncated to `38....` by the `preventWrapping` large type needed to survive its column, and sizes jumping line to line so nothing had a calm baseline. Before that, MEDIUM_PLUS on a ticker in a `MINIMIZE`-squeezed side-by-side rendered it **one character per line**. Large type in a 320px rail has almost no horizontal room.
  - **Prose:** one sentence per panel (the verdict), and within it only the verdict phrase is bold + coloured ("Fits the window —"), the rest plain ink — the mockup's own `.verdict`/`.verdict b` pattern. Everything else is a label-value pair.
  - **There is no `STANDARD_PLUS`.** The enum is exactly `SMALL, STANDARD, MEDIUM, MEDIUM_PLUS, LARGE, LARGE_PLUS, EXTRA_LARGE`; the rung above STANDARD is MEDIUM. The validator names the legal set in its error.
  - **A NARROW PANEL'S IDENTITY LINE OWNS ITS WIDTH.** Where a fixed-width item (`width: "MINIMIZE"`) sits beside identity text, MINIMIZE claims what it needs FIRST and the text truncates. `shouldWrap` would reflow but is rejected by the object validator, so the branch is made **in the expression** on the one thing that drives it — text length. In the rail: a ticker of 10 characters or fewer shares line 1 with the countdown chip; anything longer takes the line alone and the chip drops beneath. **The full identity string always wins the line.**
  - **ANY AGENT-AUTHORED CONTENT CARRIES AI ATTRIBUTION, AND IT REPLACES THE LABEL RATHER THAN JOINING IT.** A chip (`AI`, `#E7F0F6` on `#3E7396`) + the agent's name + the run time, SMALL muted — one line that is both label and disclosure. A screen that renders machine-written reasoning without saying so is making an implicit claim about its provenance; this is governance, not decoration, and it applies on every screen that shows agent output.
  - **ONE DOOR.** Where a panel excerpts a record it links to, there is exactly ONE link to that record — the primary navigation at the panel's foot. An excerpt ends with a plain unlinked `" …"` continuation cue. Two links to the same place is a decision the reader should not have to make.
  - **AN EXCERPT SKIPS WHAT ITS CONTAINER ALREADY SAID, AND DETECTS THE SKIP BY CONTENT.** Stored assessments open by restating trade id, instrument and notional — correctly, because the assessment is a standalone audit record — but a panel whose header just said all three would spend its excerpt on nothing. Start at the first sentence carrying REASONING, matched on the vocabulary of the reasoning itself (`broker confirmation lag`, `risk tier`, `twelve months`, `fail rate`, …) via `SO_textContainsAny`, never on a fixed position: "skip sentence 1" is a rule about today's authored shape and will drift. No match falls back to sentence 1, so an unfamiliar shape degrades to "show the beginning" rather than to blank. **Agent instructions are never edited to suit a screen — this is display-side selection over a record that stays complete.**
  - **A PREVIEW PANEL PREVIEWS; THE RECORD IS THE RECORD.** Stored prose is cut at the **second sentence boundary** (split on `". "` — safe because every figure in this domain has its period followed by a digit or `%`) and followed by a link to the record. Identifiers that exist only for plumbing — the case id — and identifiers already visible in the adjacent context — the trade id on the selected grid row — are **omitted from the preview** and kept on the detail screen.
  - **SAIL rich text has ONE bold** (`style: "STRONG"`), so the mockup's 650-vs-700 weight distinction cannot be reproduced; both land on STRONG. Mockup delta, not worked around.
- **GRID ROW SELECTION USES `SUBTLE_HIGHLIGHT`, NOT `ROW_HIGHLIGHT`, ON ANY GRID WHOSE ROWS CARRY SEMANTIC COLOUR.** The four styles are `CHECKBOX`, `CHECKBOX_SUBTLE_HIGHLIGHT`, `SUBTLE_HIGHLIGHT`, `ROW_HIGHLIGHT`; `ROW_HIGHLIGHT` paints a SOLID blue fill and `SUBTLE_HIGHLIGHT` a light tint. Under the solid fill the watchlist's red past-cutoff countdown, amber priority band, grey Unassigned owner and all seven status colours became unreadable at once — and those colours are how the row carries meaning. **The tint hex is platform-controlled and not author-settable; the choice between solid and subtle is the only lever, and it is a COMPONENT parameter — no site accent, theme object or branding setting is involved.** (`updateSite` exposes only name, displayName, description, webAddressIdentifier, layout, style and pages — there is no accent colour on the MCP surface at all.) Rendered by `SO_railFact` and by nothing else, so the hierarchy cannot drift per card; `tier: "KEY"` promotes a fact. Prose budget on a panel is ONE sentence — everything else is a label-value pair. Increase spacing rather than shrinking text; a panel may scroll, and cramped-beats-unreadable is false. Rich text sizes, enumerated by the platform's own validator: `SMALL, STANDARD, MEDIUM, MEDIUM_PLUS, LARGE, LARGE_PLUS, EXTRA_LARGE`.
- **RECORD ACTIONS LIVE IN THE RECORD HEADER, NOT IN A CARD ON THE VIEW — ratified 2026-09-09.** Related actions are configured as `relatedActionShortcuts` on the record VIEW and render beside the view's tab, which is where an Appian user already looks for them; the Related Actions tab is then hidden (`hideRelatedActionsView: true`), because a second copy one tab away is only a second place to look. A view builds its own `a!recordActionField` only where an action belongs to a *region* of the screen rather than to the record.
  - **MEASURED: shortcut ORDER is not author-controlled.** `relatedActionShortcuts` was sent as Record Disposition / Assign / Escalate / Add Comment and read back as Assign / Add Comment / Record Disposition / Escalate — the record type's own action order. To change what the header shows first, reorder the actions on the record type in Designer; the view parameter will not do it.
  - **THE COST IS REAL BUT SMALLER THAN IT LOOKED — CORRECTED 2026-09-24.** The action visibility expressions become the ONLY gate, and `testInterface` cannot see the result: the header renders outside the view interface, so a harness render shows no action set at all, and a visibility expression that throws hides its action and reports nothing (supplemental §4). **What is NOT true any more is that this makes the status→action mapping browser-only. sail reads the record header and drives it.** MEASURED in the Part C rehearsal: as `alex.analyst`, the hero case's header listed `Record Disposition · Assign · Escalate · Add Comment` — in the record type's own order — and `Record Disposition` was followed, filled and submitted through to a written disposition, verified by a fresh read. **So the mapping is verified as a persona through sail, per case status, like any other content-and-behaviour check; only the geometry of the header stays a browser check.**
- **A SCREEN RENDERS THE STORED DECISION; IT NEVER RE-DERIVES ONE.** The lane an analyst sees comes from the case's `status`, never from re-comparing `confidenceScore` to the gate. The two can legitimately differ — a reason override escalates a high-scoring case — and a re-derived lane announced "Released without touch · score 95" beside an Escalated chip (MEASURED on a click-through, case SO-43). Showing the gate arithmetic is fine and is the governance story; claiming an outcome the record does not carry is not. Where they diverge, say so on the screen rather than leaving it looking self-contradictory.
- **A DERIVED-STATE DISPLAY RULE CARRIES ITS STATE TO CONSUMERS RATHER THAN LETTING THEM RE-DERIVE IT** — `SO_cutoffDisplay` emits `isPast`/`hasCutoff`, `SO_autoReleaseDisplay` emits `lane`. Consumers read; they do not recompute.
- **THE WATCHLIST'S COUNTDOWNS MOVE WHEN THE PAGE LOADS, NOT WHILE IT IS OPEN — accepted by Scott 2026-11-13, no fix.** Seen in his browser check: with the watchlist left open, a countdown to cutoff does not go down, while the rows and the "last read" time refresh every 30 seconds. His ruling: "that's fairly standard for appian. the screen doesn't usually auto refresh." The likely cause is read from the source, not measured: `SO_cutoffDisplay` computes from `now()` in its own local variables, and a page evaluates a rule's local variables once (the behaviour recorded for `SO_demoRunState` under Repeatability). A session that notices this leaves `SO_cutoffDisplay` and the watchlist as they are.
- **Grids: set an explicit width on EVERY column and `preventWrapping: true` on every single-line cell.** Relative (`1X`) widths divide the available space equally and wrap headers and values mid-word ("Priorit y", "Cutof f in"). **CORRECTED 2026-09-24 — the old advice here was "one column, the widest, takes `AUTO` and absorbs the remainder", and that is NOT what `AUTO` does on a grid column.** The docs are explicit: an `AUTO` grid column's width is *"determined by the length of the longest unbroken value in that column"* — it sizes to its own content, it does not soak up slack (the absorb behaviour is `ICON` + `AUTO`), and the same page says to **avoid mixing `AUTO` with weighted widths**. Believing otherwise is what left the case-detail fails card with `Reason` at `AUTO` sized by the word "Insufficient" while `NARROW` neighbours starved — and `NARROW` has no minimum width, so they shrank to their longest word, which in the Instrument column was the ten-character HEADER. **Working form: when one column must give way to another, put every column on relative widths (`nX`) and budget them from the longest unbroken token each must seat — header included, because the header is one of the words being measured.** Reserve fixed widths for columns that genuinely always need the same space. The `a!gridColumn` width vocabulary is `AUTO, ICON, ICON_PLUS, NARROW, NARROW_PLUS, MEDIUM, MEDIUM_PLUS, WIDE, 1X–10X` — note it does **not** include `EXTRA_NARROW`, `WIDE_PLUS` or `EXTRA_WIDE`, which belong to `a!columnLayout` and are a different component's vocabulary. NOTE `truncateText` appears in the rendered grid tree but is NOT a settable parameter; a rendered-tree attribute is not proof of a writable one.
- Mockup-first: every Phase 4 interface gets an HTML mockup in `mockups/` before build. Mockups are aspirational; build to "as close as possible in SAIL" per appian-supplemental's platform deltas — information hierarchy over pixel styling. Prompts are developed collaboratively in-session, not fired as mega-prompts.
- **A MOCKUP IS THE STRUCTURAL AUTHORITY ONLY FOR THE CHANGE BEING BUILT FROM IT. ONCE THAT SCREEN IS BUILT, GATED AND VERIFIED, AUTHORITY TRANSFERS TO THE DEPLOYED SCREEN AND THE MOCKUP BECOMES A HISTORICAL DESIGN ARTIFACT — ruled 2026-09-24.**
  - **While the build is in flight** the mockup governs layout and information hierarchy, and a departure from it is a delta to be logged (next bullet). That is the whole of its authority.
