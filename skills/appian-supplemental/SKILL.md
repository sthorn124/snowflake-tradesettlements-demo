## 1. Precedence and evidence (ABSOLUTE)

**A capability is present if something on this instance uses it. It is absent only if you have tried it here and it failed. "I searched the documentation and found no component for it" establishes nothing.** The component reference describes the documented general surface, not this environment, which carries tier-gated features, plug-ins, and file-format behaviour no docs page enumerates.

Precedence order when asking "can this environment do X":
1. **A working example on this instance.** Find it (`listApplications` → `listInterfaces`/`listApplicationObjects` → read the expression), quote the mechanism. Outranks everything below, including a docs page that appears to say otherwise.
2. **Tier- and feature-specific documentation** for the capability you now know exists.
3. **A test you run here** — the smallest thing that would prove it.
4. **The general component surface.** Weakest; never sufficient for a negative conclusion.

- A negative claim in a build log or TODO must name the evidence that produced it ("tried here, failed, here is the error"), never "the docs do not mention it". (m ≤26.6.105 · method/negative-claims-name-evidence)
- **Worked example, and the reason this rule exists:** a SMIL SVG rendered broken on an agent waiting screen; a docs search found no animated SAIL component and the conclusion drawn was "nothing animates here." Wrong: another app on the same instance had been animating a waiting screen the whole time with `a!imageField(images: a!documentImage(document: cons!<GIF>), size: "FIT")` — an animated GIF through the ordinary document-image mechanism. `a!documentImage` animates fine; SVG/SMIL specifically does not. One `listInterfaces` call would have found it. (m ≤26.6.105 · sail/gif-animates-smil-does-not)
- **Where a specific worked example and a general prohibition conflict, follow the worked example and PROVE IT BY RENDER** (established on sorting: `a!sortInfo()`'s page prohibits dictionary-array sorting; the Function Recipes' `todatasubset(array, a!pagingInfo(sort:…)).data` form is correct, proven by render). (m ≤26.6.105 · sail/worked-example-over-prohibition)
- **When copying a mechanism from a working counterexample, copy its configuration too, and change one thing at a time afterwards.** (m ≤26.6.105 · method/copy-configuration-too)
- **Docs establish what a parameter IS, not what this environment CAN DO.** (m ≤26.6.105 · method/docs-define-not-enable)
- Load the applicable Dev MCP plugin skills before any object work (Appian's `appian` skill, invoked as `/appian`, whose references are in `~/.kiro/skills/appian/references/`) and consult the docs-search MCP for anything uncertain. Never guess parameter names. Project files override the pack and docs only where explicitly stricter; this file supersedes the pack where it records a measured correction. (m ≤26.6.105 · method/load-pack-first)

### Entry keys and the precedence rule

Every entry ends with a key: `(m <version> · <tool-or-area>/<slug>)`.

- **`<version>`** is the Dev MCP version the entry was last measured on, as `getDevMcpVersionInfo` reports it and the session-start report prints it (`reference/toolchain.md` §1 maps versions to build stamps). `≤26.6.105` means "measured on 26.6.105 or an earlier build; the exact one was not recorded" — the bulk stamp every pre-existing entry received on 2026-11-07. A re-measurement replaces the bound with the exact version.
- **`<tool-or-area>`** is the Dev MCP tool the entry is about (`updateSite`, `testRule`) or, where no single tool is, one of: `sail` (expression and component behaviour), `records`, `events`, `process`, `documents`, `layout`, `agents`, `integration`, `mcp` (Dev MCP behaviour not tied to one tool), `method` (a working rule rather than a platform fact).
- **`<slug>`** is two to four kebab-case words and never changes once written. The key is the entry's identity: an update to this file is merged into an installed copy entry by entry, matched on the key — new keys are appended, same-key entries are compared, and a retirement marker wins over an unretired copy unless that copy was re-measured on a newer version. Sub-bullets belong to the entry above them and move with it. Text without a key — section intros, this header — is the template's and is replaced on update, so anything that must survive an update is written as a keyed entry.
- **Retired entries.** An entry a build has measured the opposite of (core §9 step 5) is not deleted: its headline is prefixed `[RETIRED <version>: <what was observed instead>]`, where `<version>` is the Dev MCP version the contradiction was measured on, and its text and key stay. It is history, never applied. A later measurement that reinstates the behaviour rewrites the entry with a stamp newer than the retirement version, and the merge then takes the entry over the marker.
- **What wins.** This file is read alongside the pack, never instead of it: the pack says how the platform and the tools work, and this file corrects it where a measurement contradicted it. On such a point this file wins over the pack and the tool descriptions. The exception: when an entry's version is older than the running build AND the pack or the tool text now contradicts it, neither is trusted — re-measure, then correct the entry and its version. A version equal to or newer than the running build settles it in this file's favour without a re-measurement.

### What the Dev MCP transport does to data (measure, do not assume)
- **`uploadDocument`'s `content` is string-typed and round-trips through UTF-8** — bytes above `0x7F` double in size; **binary assets (GIF, PNG, XLSX) cannot be created over MCP** and must be added by hand in Designer. Confirm a hand-added binary arrived intact by reading `document(id, "size")` against the local file BEFORE wiring anything to it — that separates "feature broken" from "file corrupt". (m ≤26.6.105 · uploadDocument/utf8-no-binary)
- **`updateConstant`/`createConstant` do NOT enforce the constant's declared type.** JSON number `0` into a TEXT constant returns 200, stores a Number, reads back happily — and Designer cannot open the object at all (HTTP 500). Always read a constant back and check the JSON *type* of `value`: `"value":0` on a TEXT constant is a defect, `"value":"0"` is correct. (m ≤26.6.105 · updateConstant/type-not-enforced)
## 2. UI work: mandatory grounding

Binding before ANY edit that creates or modifies interface layout, styling, or visual design — including a one-line width or colour change — in this order:

- **Design skill first.** If a frontend design skill is installed on the machine, invoke it first. Under Claude Code this step loaded the frontend-design plugin; that plugin has no Kiro equivalent in this port, so on a machine without one this step is a no-op and the next two entries carry the grounding. (m ≤26.6.105 · layout/design-skill-first)
- **Read the pack's layout files before editing.** Read the relevant pack references before editing. Every layout edit: `interface-generation-checklist.md` plus the file for EACH layout in play (`layouts/columns-layout-instructions.md`, `layouts/sidebyside-layout-instructions.md`, `layouts/card-layout-instructions.md`, `layouts/pane-layout-instructions.md`, `layouts/section-layout-instructions.md`, `layouts/header-content-layout-instructions.md`, `layouts/form-layout-instructions.md`, `layouts/tab-layout-instructions.md`, `layouts/wizard-layout-instructions.md`). New interface: add `interfaces.md`, `sail.md`, `ui-patterns.md`. Rich text with links/colour/truncation: `components/rich-text-instructions.md`. Before done: `sail-verification-checkpoint.md`. Where a named file is absent or the pack doesn't cover the question, substitute docs-search and say you did. Cite no path you have not just listed. (m ≤26.6.105 · layout/read-pack-layout-files)
- **Uncertainty goes to docs-search before the edit.** Any uncertainty about parameter semantics, width allocation, wrapping, or component interaction goes to docs-search BEFORE the edit, and the documented answer is stated in the response. "It renders in the component tree" is not evidence a keyword is accepted; "accepted keyword" is not evidence it is usable in this position. (m ≤26.6.105 · layout/docs-search-before-edit)
- **Every summary of UI work separates verified from unverified.** Tree and harness prove structure (component order, colour values, requested widths, error-free evaluation); they carry no geometry — no pixel widths, line breaks, overflow, focus/hover, or link colour against site accent. Those are browser-only checks and must be listed as such. Never describe a layout as confirmed on harness evidence alone. (m ≤26.6.105 · layout/tree-is-not-geometry)
- **THE TREE WILL LET YOU REPORT A LAYOUT THAT DOES NOT EXIST, so read the ATTRIBUTE, never the item count.** Worked example, measured: a rich text field built as `{item, char(10), item, char(10), item}` renders as three separate text entries in the tree **whether it stacks or collapses**, because `char(10)` is data, not layout. Set `preventWrapping: true` on that field and it renders as ONE truncated line — the docs are explicit that *"each paragraph or list item will truncate to a single line"*, and a `char(10)` inside a rich text value IS a paragraph break. Counting three items in the tree and reporting "stacked" is reading structure and claiming geometry; it shipped a broken cell past a render check and a written close-out. **The tree DOES expose `preventWrapping` per field** — so this one is checkable without a browser, and the check is the attribute. Generalise: when a parameter's whole job is to change geometry, verify the parameter's value, not the shape of the content it governs. (m ≤26.6.105 · sail/prevent-wrapping-attribute-not-count)
  - Related trap from the same family: `preventWrapping` is documented as incompatible with `"MINIMIZE"`-width side-by-side items, and it turns overflow into an ellipsis rather than a wrap — so it is the wrong tool for anything that must stay fully legible, and the right one only for a genuinely single-line cell.
- **Checklist and validation before done.** Every generated interface goes through the pack's interface generation checklist and `validateExpression`/`testInterface` (`diagnostics.error: null`) before it counts as done. (m ≤26.6.105 · layout/validate-before-done)

## 3. Dev MCP mechanics and limits

- **GROUP MEMBERSHIP IS READABLE OVER THE DEV MCP FROM 26.6.90 AND WRITABLE FROM 26.6.95; THE 403 WALL WAS THE PREVIOUS GENERATION.** Measured: on the previous generation `createGroup` succeeded, but the name-addressed `addGroupMembers`, `getGroup` and `listGroupMembers` all returned **HTTP 403 "Group not found or access denied"**, even against long-existing groups the same account listed. From 26.6.90 the group tools are UUID-addressed and reads work: `listGroups(appUuid)`, `getGroup(uuid)` and `listGroupMembers(uuid, directOnly, memberType)` return the group and its members (display names come back empty; `directOnly` separates explicit from inherited membership). On 26.6.95, `addGroupMembers(uuid, members)` added three users and each read back as a direct member (measured on one Cloud site, 2026-09-21; re-verify per instance). `removeGroupMember` is unexercised. **Working form:** create and populate the group over MCP, then prove membership with `listGroupMembers(uuid, directOnly: true)`, never by the add's `status: success`. **On a server older than 26.6.90 the wall stands:** a group created over MCP is EMPTY and a site gated on it is invisible to everyone, so hand "add the first member" to a human in Designer. Record: `reference/mcp-capability-boundaries.md` §6. (m 26.6.95 · addGroupMembers/membership-over-mcp)
  - Two mechanics measured alongside it: a GROUP-typed constant takes the group's **NAME**, not its UUID (`value: "<Group Name>"` succeeds where the UUID fails with "Group not found"); and a freshly created group is briefly invisible to other calls, so a first attempt may fail purely on timing — re-list before concluding anything.
- **Objects outside an application are effectively unfindable over MCP** — nothing lists them, no lookup by name; `getExpressionRule` returns the same 403 for "does not exist" as for "is not a rule". Designer CAN search by name: an orphaned object is a thirty-second fix there, an unbounded hunt here. (m ≤26.6.105 · mcp/orphans-unfindable)
- **`getObjectDependents` is the only reverse index** — finds objects an application does not list, and is the working substitute where `listAgents`/`getAgent` fail (returns the agent as an `AI_AGENT` dependent with its UUID). (m ≤26.6.105 · getObjectDependents/only-reverse-index)
- **`getProcessModelNodeTypeSchema` with an AI agent's `referenceUuid` adds nothing, and the bare answer looks like a complete one.** For an Execute AI Agent node type it returns the five schema inputs and the five built-in outputs (`Success`, `ErrorMessage`, `RunSummary`, `RunId`, `AiActionsConsumed`) and echoes `referenceUuid` back — no declared agent output, no `_agentInput_` ACP. Measured twice in one session on the same agent, **once while it declared no outputs and again after it declared twelve: byte-identical responses**, so the emptiness is not the agent's. The bundle only forwards the parameter as a query arg, so the behaviour is the plugin's. Against the tool's own text, which says `referenceUuid` enriches the schema "e.g., integration inputs for Call Integration, subprocess PVs for Subprocess" — both of which do work (a subprocess's parameters come back as named inputs and outputs); an agent is the reference type that does not. **Working form:** an agent's declared surface is readable from neither the agent (`getAgent` → HTTP 401) nor this schema call; map its input by convention (`_agentInput_` + the declared input name) and read anything else off the node after a Designer edit has generated it. (m 26.9.5 · getProcessModelNodeTypeSchema/agent-reference-adds-nothing)
- **`getObjectDependents` resolves no AI agent UUID, and its refusal reads like a wrong or deleted identifier.** Asked for the dependents of an agent whose UUID `listAgents` had returned seconds earlier, it raises `No design object or data type with that identifier, its type could not be determined, or it names a deleted data type: <uuid>`. The bundle's `tools/objects.py` maps that message from the endpoint's **HTTP 404**, so none of the three causes the message offers is what happened — the type simply does not resolve. Against the tool's own text, which says it answers "what breaks if I change or delete this" **for any design object** and that "for a UUID the server resolves the object type itself". **Consequence:** there is no reverse route from an agent to whatever binds it; to find the process model holding its node, read the models. **This narrows `getObjectDependents/only-reverse-index`, it does not retire it** — that entry runs *towards* the agent (a tool rule's dependents include it as `AI_AGENT`) and still holds; the direction measured here is *from* the agent. (m 26.9.5 · getObjectDependents/agent-uuid-not-resolvable)
- **`listObjects` by type `AI_SKILL` or `AI_AGENT` returns zero whether or not such objects exist.** Enumerate with `listAiSkills` and `listAgents` scoped by `appUuid`, or `getObjectDependents` from a tool rule. A zero from `listObjects` on these types is not a finding and is never reported as "none exist". (measured 26.6.105; re-hit 26.9.5 build `20261026-140102`, where a session reported "no AI objects in the environment" from it.) The per-application `aiSkills`/`agents` counts from `listApplicationObjects` came back zero in the same session and are unverified; treat them the same way until measured. (m 26.9.5 · listObjects/ai-types-return-zero)
- **`listProcessInstances` IS NOT SORTED NEWEST-FIRST ACROSS ENGINE PARTITIONS, SO COUNTING A RUN'S INSTANCES OFF THE FIRST PAGE UNDERCOUNTS — AND THE SHORTFALL READS AS A PLATFORM FAULT.** Measured on one model whose dispatcher had just started 21 child instances: they came back split across three `processId` series, and the first page of 30 held only **14** of them, with the remaining 7 appearing *below* instances from three hours earlier. The natural reading — "only 14 of the 21 started" — is a throttling or a concurrency conclusion, and it is wrong; ordering is newest-first *within* each engine partition and the partitions are concatenated, so a recent instance can sit anywhere in the result. **Against the tool's own docstring**, which says it "Returns a paginated envelope of instance summaries sorted newest-first by start time"; the bundle's `tools/process_history.py` forwards `limit` and `offset` to the plugin and returns the response verbatim, performing no sort of its own, so the claim describes an endpoint that does not honour it globally. **Working form: page until the time window you care about is exhausted and select by `startTime` rather than by position, and corroborate the count with something that does not depend on this ordering** — a per-record-type row count, or one audit row per unit of work. The same caution applies to any conclusion drawn from "the newest N" of this tool. (m 26.9.5 · listProcessInstances/order-not-global)
- **THE FIRST READ AFTER AN `updateInterface` CAN RETURN THE VERSION BEFORE IT — BOTH `testInterface` AND `getInterface` — SO A FLIP-RENDER-RESTORE CAN LOOK FAILED, OR PASSED, ON THE WRONG VERSION.** Measured three times on two interfaces in one session. (1) A harness interface gained an optional input; the first `testInterface` passing that input rendered the old branch, and the identical call repeated rendered the new one. (2) A record-view interface was saved with a hidden tab flipped on for a probe; the first render through a wrapper showed the default tab and none of the probed content, the next render showed it. (3) The same interface restored to the saved source: the update returned the new `versionId`, and a `getInterface` straight after returned the **probe** version, with its flipped line, while a second `getInterface` returned the restored source byte-identical to the saved copy. Nothing in either tool's text says reads are eventually consistent, and the update response reports the new version as current, so the stale first read is indistinguishable from a write that did not take. **Working form: after any `updateInterface`, read twice and trust the second, and before trusting a render check that one string you know you changed appears in it** (the same check `method/harness-regenerates-with-source` asks of a harness). In a flip-render-restore, verify the restore by a byte comparison on a second `getInterface`, never the first. Expression rules were not seen to do this in the same session; re-verify per object type. (m 26.9.5 · updateInterface/first-read-may-be-stale)
- **A zero-byte document is not creatable** — seed files need real bytes and therefore a real job. (m ≤26.6.105 · uploadDocument/zero-byte-rejected)
- **A `createProcessModelNode` that FAILS VALIDATION MAY still have created the node — check before retrying.** The call returns HTTP 500 (`Error creating node: Process Model contains errors/warnings: …`), which reads as a rejection, but the failure is not reliably a rollback: a `WriteRecordsWithEvents:400` failure left the node persisted with the payload as sent, while a `Non-nullable input ACP(s) … must not be null` failure on a Send E-Mail node left nothing behind. **Both outcomes occur, so never assume either.** Call `getProcessModelNode` first: if the node exists, recover with `updateProcessModelNode` (or delete it) — a blind retry fails with `Node with id N already exists` and leaves an invalid node in the model; if it does not exist, re-issue the create. Note that `data` is a FULL REPLACEMENT of the data section, so a recovery call must resend every input, not just the one being fixed. (m ≤26.6.105 · createProcessModelNode/failed-create-may-persist)
- **WHERE A COMPONENT IS CONSTRUCTED IS PART OF WHETHER IT IS VALID — not just how.** Three measured instances, one rule: some components read variables that only exist while a specific parent is evaluating them, so building them anywhere else fails. (m ≤26.6.105 · sail/construction-site-matters)
  - **A record action item cannot be built in a local variable.** `local!actions: a!flatten({a!recordActionItem(...)})` passed to `a!recordActionField(actions:)` fails the object validator with `Unresolved reference(s): recordAction!openActionsIn, recordAction!visibilityRefreshCounter`. Construct the items INLINE in the `actions:` parameter; compute the conditions that select them as locals instead.
  - **Related-action shortcut ORDER is not author-controlled.** A record view's `relatedActionShortcuts` accepts an ordered list and does not honour it — the readback returns the RECORD TYPE's own action order. Reorder on the record type (a Designer step; no MCP call reorders record actions) or accept the order you have.
  - **Consequence worth planning for: actions rendered by the record header are invisible to `testInterface`**, which evaluates only the view's own expression. The action set itself is verifiable per persona through the sail CLI, which lists the actions a record view offers to the account that reads it (measured: 29 actions for the design account and 26 for a persona on the same record; sail evaluation S32, `examples/persona-verification-walkthrough.md`). How the set changes with record status remains unmeasured. A visibility expression that throws still hides its action silently (§4). Weigh that against the convenience before moving actions out of a view.
- **AN OPTIONAL INPUT CAN BE ADDED TO A SHARED INTERFACE RULE WITHOUT TOUCHING ITS CALLERS — omitted inputs arrive NULL, not an error.** Measured: a `tooltip` input was added to a KPI-tile rule with four existing seven-argument calls on a separate, already-signed-off screen; that screen re-rendered with `diagnostics.error: null` and unchanged output. The widely-repeated "interface rules require every declared parameter to be passed" is true only of a **zero-argument** call to a rule that declares inputs (`rule!Foo()` fails); it is not true of a partially-argumented one. This matters because the over-broad version makes people edit ratified objects out of caution they do not owe. **The real risk is silence, not failure:** a null arriving where a boolean `showWhen` was expected hides a component without erroring, so add the input with a defaulting read (`a!defaultValue(ri!new, <safe>)`) and the old callers keep their old behaviour exactly. (m ≤26.6.105 · sail/optional-input-arrives-null)
- **`updateSite(pages:)` IS A FULL REPLACEMENT AND REGENERATES EVERY PAGE'S URL STUB.** Adding one page by resending the existing list changed the untouched pages' `webAddressIdentifier` values (e.g. `7K2G7Q` → `hDGI5A`), so any bookmark, deep link or documented URL into that site breaks. Resend the full list — omitting pages deletes them — but expect new stubs and re-check anything that hardcodes one. (m ≤26.6.105 · updateSite/pages-full-replacement)
- **Metadata is not the object's state** — `getDocument` can report `extension: null` where runtime `document(doc, "extension")` returns a value; resolve at runtime, never by believing the readback. (Same class as column widths, §7.) (m ≤26.6.105 · getDocument/metadata-not-state)
- **A generated record type's Record List column configuration is not exposed over MCP** — default columns (raw FK integers) until set in Designer. Nothing errors. (m ≤26.6.105 · records/list-columns-designer-only)
- **Grid data binding, corrected rule:** grids over record data bind `data:` DIRECTLY to the record type, fully UUID-qualified — REQUIRED where native search, refresh, export, or per-column user filters are needed. The query-into-a-local pattern (`a!queryRecordType(...).data`) applies only to grids/components over assembled or joined non-record data. (Supersedes the older blanket "always query into a local" guidance. If a record-bound grid fails MCP validation in a new environment, re-probe before assuming either pattern.) (m ≤26.6.105 · sail/grid-binds-record-type-directly)
- **All record/field references fully UUID-qualified**: `'recordType!{<rtUuid>}<Name>.fields.{<fieldUuid>}<field>'` — NOT the datatype URN. (m ≤26.6.105 · sail/uuid-qualified-references)

### Validation and testing
- **`validateExpression` evaluates BOTH branches of an `if`** (guarded-`1/0` probes are worthless), returns errors only, never values. **The record-view and interface validators do it too**, which is what makes a conditional guard unable to keep an empty list out of a query filter; see §4's record-view entry for the consequence and the working form. (m ≤26.6.105 · validateExpression/both-if-branches)
- **BECAUSE IT RETURNS ERRORS AND NOT VALUES, ASSERT BY MAKING A FALSE ASSERTION *ERROR*: `index({"ok"}, if(<assertion>, 1, 0))`.** `index(list, 0)` with no default fails with `Invalid index (0) for list: valid range is 1..1`, so the expression validates clean when the assertion holds and errors when it does not: a whole truth table evaluated through `validateExpression` with no object created and nothing to delete, which is what makes it usable where deletes are denied by default (core §6) or where a throwaway object would have to be cleaned up under core §12. Both `if` branches are the constants 1 and 0, so the both-branches rule above is harmless here. **Always run the negative control**, the same harness with one expectation deliberately wrong, or a harness that silently cannot fail reads exactly like a pass. Measured across two builds. (m 26.6.105 · validateExpression/assertion-by-index-error)
- **Test inputs are LITERALS for `testRule` AND `testInterface`** — an expression passed as input renders as though empty, silently. Query-dependent objects are verified through a wrapper interface, which does evaluate references. (m ≤26.6.105 · testRule/inputs-are-literals)
- **Keyword strictness varies by validator, and the gaps ship broken objects silently:** object validators (`createExpressionRule`, `createInterface`) reject unknown keywords; `createSite` and `addRecordTypeAction` do NOT — a visibility/security expression with a wrong keyword (e.g. `a!isUserMemberOfGroup(groupsToCheck:…)`; the real parameter is **`groups`**) evaluates with the argument missing, typically returns false, and silently hides what it was meant to gate. Function keyword typos can no-op without error. The MCP validator rejects undocumented FUNCTIONS outright. (m ≤26.6.105 · mcp/keyword-strictness-varies)
- **`validateExpression` IS NOT A KEYWORD CHECK, AND THE RENDERED TREE IS NOT A PARAMETER LIST.** Three measured instances of the same shape: `contentsWidth` on `a!headerContentLayout`, `truncateText` on `a!gridColumn`, and `shouldWrap` on `a!sideBySideLayout` — each appears in the component's own rendered tree, each is accepted by `validateExpression` with `hasErrors: false`, and each is rejected by the OBJECT validator (`Unrecognized Keyword …`). Only the object validator is authoritative; an attribute you can read back is not necessarily one you can set. The consequence is design-level, not cosmetic: `shouldWrap` would have let a side-by-side reflow, and without it a `width: "MINIMIZE"` sibling starves the flexible item beside it — with `preventWrapping` on, that overflow becomes a silent ellipsis rather than a visible break. When a layout cannot reflow, branch in the EXPRESSION on whatever actually drives the fit. (m ≤26.6.105 · validateExpression/not-a-keyword-check)
- **Therefore visibility and security expressions are verified BEHAVIOURALLY, never by validation alone:** read the stored expression back, confirm the keyword, then click as a member and as a non-member. Nothing automated distinguishes "hidden by rule" from "hidden by broken rule". (m ≤26.6.105 · method/visibility-verified-by-click)
- **Expression rules validate at save time with no ContentService and no `env!`** — a bare `getpdftext()` or `a!callLanguageModel` cannot live in one; probes of this class are throwaway interfaces. **A RECORD QUERY IS NOT IN THAT CLASS: `a!queryRecordType` lives and evaluates in an expression rule, and shared queries belong there.** This clause previously named a record query alongside the other two and was wrong. Measured on DevMCP 26.6.110 across two sessions and ten rules: a COUNT aggregation over a row-secured record type; three queries with relationship traversal in both `fields:` and `filters:`, a sort and an `a!forEach` over the result; a self-referencing parent traversal two levels deep; an "in" filter against a computed id list; and a rule composing a 1,500-character text block out of four other query-bearing rules — every one saved clean through `createExpressionRule` and returned correct values through `testRule` in 60–180 ms. `a!toJson` is callable from one too. **Working form:** implement a shared query ONCE as an expression rule and verify it with `testRule`; reserve throwaway interfaces for the ContentService and model-call cases. The 5-second evaluation cap (next entry) still applies, so a rule fanning out over a large table is a different problem from this one. (m 26.6.110 · createExpressionRule/record-queries-allowed)
- **Design tooling caps one evaluation at 5 seconds; `testInterface` tolerates longer** — the interface route is the only legal and measurable home for real model calls. (m ≤26.6.105 · testInterface/five-second-cap)
- **`testProcessModel` cannot pass a RECORD-TYPED parameter, so any model whose parameter is a record value is not exercisable end to end over MCP.** The `inputs` map is marshalled into an `a!map()` of LITERALS: a string value is quoted, never evaluated (`"=a!update(...)"` arrives as Text and the Write Records node rejects it with `Each item within the input "Records" must be a record data type. Received: Text`), and a nested object whose keys carry the UUID-qualified field syntax breaks the map construction itself (`Invalid operator 'open_brace'`). **A third shape is the dangerous one: a nested object with PLAIN field-name keys marshals cleanly and reaches the node as a Map** (`Received: Map`) — so the process STARTS, runs every node upstream of the write, and only fails at the write itself. Nodes UPSTREAM of the write still run and their PVs read back, so the harness proves the pre-write half and nothing after it — and note what that means for a model whose upstream nodes compose from the payload: they compose from a value they could not read, producing a degraded-but-plausible result (measured: an event sentence composed with both of its real values missing, reading as a plausible generic sentence). If any such node WROTE rather than composed, the harness attempt would have left a garbage row behind. Options, in order: exercise the branch that skips the write (cancel/empty path) as a non-regression check; mirror the post-write nodes' expressions in a throwaway expression rule with real values to prove the composition; and run it end to end — **through the sail CLI as a persona when the model's start form is reachable from a site** (measured: related-action start forms driven and submitted as a persona, each write confirmed by a fresh read of the record and its activity entry; sail evaluation S11, S13, S19, `examples/persona-verification-walkthrough.md`), otherwise in a browser checklist. Attended mid-flow tasks remain browser-verified until measured. Say which of the three was done — do not report a partial run as a path exercised. (m ≤26.6.105 · testProcessModel/no-record-typed-inputs)
- **A `testProcessModel` TRANSPORT `ReadTimeout` IS NOT A FAILED RUN: THE PROCESS MAY HAVE COMPLETED IN FULL, AND RE-RUNNING IS THE DANGEROUS INSTINCT.** When the wait exceeds the requested `timeoutSeconds` the call raises `Network error: ReadTimeout` rather than returning its own `timedOut` diagnostic, so the response carries no `status`, no `processVariables` and no indication of how far the run got — while the engine carries on to completion regardless. Measured in two sessions on two different models: a reset that had deleted and restored every row it was asked to, and a 65-second dispatcher that had started all 21 of its children; both reported `COMPLETED` on readback after raising `ReadTimeout`. **The trap is that the error reads like "it did not run", so the reflex is to call it again — which on a non-idempotent model writes everything twice.** Note that the tool *does* expose a `timedOut` field, which is what makes the transport error look like a different and worse class of failure than it is. **Working form: treat `ReadTimeout` as "outcome unknown", never as failure.** Read the instance back (`listProcessInstances` on the model, newest window — but see `listProcessInstances/order-not-global`), then count per record type, and only then decide whether anything needs re-running. (m 26.9.5 · testProcessModel/readtimeout-run-may-complete)
- **`testRule` cannot pass a Date input** (arrives as an integer; `todate()` doesn't rescue; `date(y,m,d)` as input isn't evaluated). Embed `date()` literals in a harness expression; the runtime PV path is fine and is what ships. (m ≤26.6.105 · testRule/no-date-inputs)
- **Icon names are verified via docs-search before use** — a plausible-sounding invalid icon (`chart-line`) fails the whole interface at create time. (m ≤26.6.105 · sail/icon-names-fail-at-create)
- **`a!wizardLayout` evaluates ONLY the active step** — type errors in steps 2..n save clean and fail on first Next; `testInterface` renders only the active step too. Any step beyond the first needs a companion verification interface mirroring its expressions with realistic values. Wrap values pulled from maps with `todecimal()`/`tointeger()`/`todate()` before arithmetic. (m ≤26.6.105 · sail/wizard-active-step-only)
- **A GENERATED VERIFICATION HARNESS GOES STALE THE MOMENT ITS SOURCE CHANGES, AND IT FAILS SILENTLY AND POSITIVELY.** The companion-interface technique above produces an artefact that mirrors a screen; describing it as "generated from the source, so it cannot drift" is true only while somebody re-runs the generator. When they don't, the harness keeps evaluating to `error: null` **against a screen that no longer exists** — a green light for yesterday's build, which is worse than no harness, because a red one would at least be noticed. (measured: a step harness was still rendering a two-way heading five days after the source became three-way; nothing anywhere reported a problem.) **Tie the regeneration to the same change that edits the source** — a harness re-synced in the commit that changed the screen, never "next time we look at it" — and before trusting any harness render, check one string you know you changed actually appears in it. A harness is a mirror, and an unmaintained mirror shows the room as it was. (m ≤26.6.105 · method/harness-regenerates-with-source)
- **A STEP'S OWN PROPERTIES — `disableNextButton`, `validations` — ARE INVISIBLE TO BOTH ROUTES.** `testInterface` never reaches an inactive step, and a companion interface does not help either: it copies the step's CONTENTS into a form layout, so the `a!wizardStep` properties are not in it. A navigation gate is therefore unverified by every render you can run. Mirror the gate expression in a THROWAWAY EXPRESSION RULE with one boolean/text input per term and evaluate the truth table — allowed and blocked states both — then delete it. Cheap, exhaustive, and the only automated evidence a gate does what it reads like. On a wizard step, the button's actual disabled state stays a browser check. The sail CLI reports a button's disabled state on ordinary forms — `[DISABLED]` in its listing, and the flip in its diff when a selection enables it (measured: sail evaluation S16, `examples/persona-verification-walkthrough.md`) — but wizard steps are unmeasured. (m ≤26.6.105 · sail/wizard-step-gate-unverifiable)

## 4. Expression and SAIL measured traps

### Silent wrong answers — the call succeeds and the number answers a different question
- **`.totalCount` RETURNS `-1`, AND THE USUAL WORKAROUND DOES NOT SCALE — COUNT WITH AN AGGREGATION.** Re-measured on a 50,000-row table at `batchSize: 1`: every `.totalCount` came back **-1**, and a readiness screen confidently reported "Baseline rows -1, expected 50,000" in red. `count(a!queryRecordType(…, batchSize: 500).data)` and `a!forEach`+`sum` work only where the answer is under the batch size, so neither reaches a real table. **The tool that does is `a!aggregationFields` with a COUNT measure** — one row holding the number, no row transfer: `a!queryRecordType(recordType: …, fields: a!aggregationFields(measures: a!measure(field: …, function: "COUNT", alias: "n")), filters: …, pagingInfo: a!pagingInfo(startIndex: 1, batchSize: 1)).data`, then `index(index(…, 1, null), "n", 0)`. Filters apply to the aggregate exactly as to rows. Reserve `count(...)` for a list you already hold. (m ≤26.6.105 · sail/totalcount-minus-one)
- **`count()` returns 1 on a list of DICTIONARIES** (what `a!fromJson` produces) — count through `a!forEach`. (m ≤26.6.105 · sail/count-of-dictionaries)
- **`list = {}` compares ELEMENT-WISE** — `a!isNullOrEmpty` is the scalar test. (m ≤26.6.105 · sail/empty-compare-elementwise)
- **`tostring()` on a LIST joins it into one delimited string while `tointeger()` maps element-wise** — the joined value makes `wherecontains` a guaranteed miss. (m ≤26.6.105 · sail/tostring-joins-list)
- **A LOCALLY-SOURCED `a!gridField` IDENTIFIES ROWS BY POSITION, NOT BY YOUR KEY.** The rendered tree reports `identifiers: [1..n]`, so `selectionValue` must be a ROW INDEX; hand it a business key and it matches nothing — no highlight, no error, and `selectionSaveInto` still returns indices, so a screen can look wired and select nothing. Measured both ways on a three-row local list: `selectionValue: 2` renders `selected: [2]` and highlights; `selectionValue: 92` (a real id in the data) renders `selected: [92]` and highlights nothing. Where the selection must survive filtering, keep the business key in a separate variable and derive the index from it each render. (m ≤26.6.105 · sail/local-grid-selection-by-index)
- **`index(map, "key", default)` CANNOT TELL "KEY ABSENT" FROM "VALUE EQUALS THE DEFAULT", so handing a function the WRONG MAP SHAPE degrades silently instead of failing.** Measured: a parse gate returned a WRAPPER — `{ looksJson, candidate, parsed }` — around the object a consumer wanted; the wrapper was passed straight through, every `index(wrapper, "<realKey>", {})` returned its default, and the consumer produced a full, plausible, entirely wrong result (a full multi-row result with none of the structure the payload actually carried) with no error anywhere. **A defaulted read is an assertion that the key is optional. Where it is not optional, assert the shape instead** — check one key you know must be present before using the map, or have the wrapper-returning rule expose the inner value under a name the caller cannot get wrong. Same family as the entries above: the call succeeds and answers a different question. (m ≤26.6.105 · sail/defaulted-read-hides-wrong-shape)
- The defence: check the question matches the claim before trusting the result. `-1` is not a count; a clean validation is not a correct keyword. (m ≤26.6.105 · method/match-question-to-claim)

- **AN HTTP INTEGRATION'S "AUTOMATICALLY CONVERT … TO JSON" CAN SHOW CHECKED AND STILL SEND THE APPIAN TEXT RENDERING OF A MAP.** Measured on an integration configured over the Dev MCP; the configuration, the contradiction and the fix follow. (m ≤26.6.105 · integration/auto-json-sends-text-form)
  - Content Type JSON, the checkbox shown checked in Designer, body expression an `a!map(…)`.
  - The remote API received `[key:value,…,nested:[k:v]]` — Appian's text form, not JSON — and rejected it with a 400.
  - Appian raised nothing; the only signal was the remote's error quoting the body.
  - This contradicts the Integration Object docs, which say a dictionary passed with JSON selected is converted automatically. **Working form: make the body expression return the finished JSON string** — `a!toJson(<full payload map>, false)` — with automatic conversion OFF and Content Type still JSON.
  - Two sub-facts from the fix: `a!toJson()` rejects a bare Text value (it needs a map, dictionary, CDT, record or list); and a JSON object key that is not a valid SAIL identifier (e.g. `"1"`) is built with `a!update(a!map(), "1", value)`, which `a!toJson` emits as an object key.
  - Prove the body by evaluating the same expression in a throwaway rule, not by reading the integration back (next entry).
- **AN INTEGRATION'S EXPRESSION PROPERTIES READ BACK OVER THE DEV MCP WITH LEGACY VERSIONED FUNCTION NAMES THAT DO NOT MATCH WHAT RUNS.** So a readback of an integration is not a copy of the integration: verify its expression by evaluating the as-sent text in a throwaway rule, verify flags visually in Designer, and treat one live call as the proof. (m ≤26.6.105 · getIntegration/readback-not-a-copy)
  - **The rewrite:** sent `a!toJson(…)` / `a!fromJson(…)`; both `updateIntegration` and a fresh `getIntegration` return `a!toJson_17r1(…)` / `a!fromJson_19r2(…)`.
  - **Not evaluable as written:** an expression rule containing the readback text verbatim fails validation (`Rule 'tojson' has 1 parameters, but instead passed 2 parameters`), yet the stored two-argument call executed at runtime.
  - **Booleans too:** a boolean property set to `false` reads back `null`.

- **`regexsearch` RETURNS A MAP PER MATCH, NOT A STRING, AND ONLY THE FIRST ONE — and treating a hit as text produces a plausible wrong number in silence.** The Regex Functions plug-in's `regexsearch` returns one map per match with keys **`match`, `startPosition`, `endPosition`**. Used as text, a hit stringifies to `[endPosition:36,match:EUR 312,600.00,startPosition:22]`, so the natural "split it and take the last token" produces **`312600.0022`** out of `"312,600.00,startPosition:22]"` — a figure that reads as correct, raises nothing, and passes every assertion that expects *no* value. Measured on two independent call sites with two different patterns (a UUID and a currency-plus-amount) in one rule: only the positive control caught it, because both negative specimens expect nothing and still passed. **Separately, the function returned only the FIRST match regardless of its third argument** (probed with the third argument at 20 against text carrying two distinct UUIDs and two distinct amounts; one candidate of each came back), so **ambiguity cannot be detected by asking the regex for every match**. The plug-in is not in Appian's documentation — docs-search returns nothing for it — so there is no stated contract for the third argument to contradict; re-verify per instance and per plug-in version. **Working form:** extract `index(hit, "match", "")` from every hit before touching it, never case-fold a hit (only an extracted string — `upper()` on a hit upper-cases the key names too), and where a count of candidates matters, **scan tokens with an anchored pattern** rather than asking for all matches: one mechanism that both finds the value and counts honestly. (m 26.9.5 · sail/regexsearch-returns-maps)

### Queries
- **Always pass `fields:` to `a!queryRecordType()` and `a!queryRecordByIdentifier()`.** Without it they return the identifier ONLY and every other field is null — no error, correct row counts, working filters, blank screen. Include related-record fields in the same list. The single most expensive gotcha measured: it shipped an apparently-verified dashboard rendering empty against real data. (m ≤26.6.105 · sail/query-without-fields-returns-ids)
- `a!queryRecordType()` has no top-level `sort:` — sorting goes inside `pagingInfo: a!pagingInfo(sort: a!sortInfo(...))`, list of sortInfo for multi-key. (m ≤26.6.105 · sail/sort-inside-paginginfo)
- **A DELIBERATE "RETURN EVERYTHING" DECISION EXPIRES WHEN THE DATA SET IT WAS REASONED ABOUT SPLITS, AND NOTHING FAILS WHEN IT DOES.** The rule is not "always filter": it is that a safeguard justified by *"returning all of it and returning the relevant subset are the same list today, so the safer one is free"* carries a hidden dependency on that coincidence. When a second category is added the two stop coinciding — and the code still returns a correct SUPERSET, so no test breaks, no error is raised, and the cost surfaces somewhere else entirely (measured: an unfiltered reference list handed to an LLM tool tripled the agent's reasoning steps and its runtime, with the query itself still returning in milliseconds). **Write the coincidence into the comment that justifies the decision** — "these are the same list while X holds" — so the day it ends is a search hit rather than a regression hunt. Same family as the two entries around it: a query returning MORE than was asked, with nothing complaining. (m ≤26.6.105 · method/superset-safeguard-expires)
- **THE RECORD-VIEW VALIDATOR EVALUATES THE VIEW WITH ITS IDENTIFIER NULL, AND EVERYTHING FED FROM THAT IDENTIFIER MUST BE GUARDED — not just the obvious call.** `a!queryRecordByIdentifier()` ERRORS on a null identifier, and so does any `a!queryFilter(operator: "=")` whose `value` comes from `rv!record` or the view's rule input (`"value" must not be null or empty`). The failure is at SAVE time, not at run time: the view simply will not save, on a screen that renders perfectly under `testInterface` with a real id. Guard the whole block once — `local!hasId: not(a!isNullOrEmpty(ri!id))`, then `if(not(local!hasId), {}, a!queryRecordType(…))` — rather than each call. **The same nullness reaches related-action visibility expressions**, which dereference `rv!record` and are evaluated by the platform with no error surface at all: a visibility expression that throws does not report, it just hides the action. Null-guard those too, and verify them by clicking, never by validation (see also the keyword-strictness entry — visibility expressions are the one place where two different silent-failure modes overlap). (m ≤26.6.105 · addRecordTypeView/null-identifier-at-save)

### Types and functions
- **SIBLING LAYOUTS DO NOT SHARE A WIDTH OR TYPE VOCABULARY, AND THE VALIDATOR IS THE ONLY PLACE THAT SAYS SO.** Two measured instances, one rule: `a!sideBySideItem(width:)` accepts ONLY `"AUTO"`, `"MINIMIZE"` and `"1X".."10X"` — the named widths that `a!columnLayout` takes (`NARROW`, `MEDIUM`, `MEDIUM_PLUS`…) are rejected outright, on a layout that reads almost identically; and `union(list, {})` fails with *"Invalid types, can only act on data of the same type (Text, Any Type)"* because `{}` is Any Type, so the working distinct idiom is `union(list, list)`. **Never carry a literal across from a neighbouring component because it looked the same.** The validator names the legal set in its error, which makes this cheap to check and expensive to assume. (m ≤26.6.105 · sail/width-vocabulary-per-component)
- **`min()`/`max()` over DATES returns Number (Decimal), not Date**; over an INTEGER list also Decimal (then `wherecontains` refuses it — wrap `tointeger()`). Take extremes over integer day offsets and index the Date list by position. (m ≤26.6.105 · sail/min-max-return-decimal)
- **Date minus Date returns an Interval** (prints `21::00:00:00.000`) — wrap day counts in `tointeger()`. (m ≤26.6.105 · sail/date-difference-is-interval)
- **SECONDS BETWEEN TWO DATE AND TIME VALUES: `todecimal()` ON A DATE AND TIME IS A DAY NUMBER, SO THE DIFF IS `tointeger(round(86400 * (todecimal(end) - todecimal(start)), 0))`.** The docs give no general-expression answer: the only date-diff function with a `"SECOND"` interval is `a!customFieldDateDiff()`, which its own page restricts to real-time custom record fields, and subtracting the two values directly yields an Interval whose unit is days (entry above). Measured: 41 for a 41-second interval, and 98107 for 1 day 3 h 15 m 7 s, with a deliberately wrong expectation failing as the control. Use it for durations a process measures across its own nodes (a model call, a wait); keep `round()` outside `tointeger()`, which truncates. (m 26.6.105 · sail/seconds-between-datetimes)
- **`tointeger()` ROUNDS** — use `floor()` for whole units. (m ≤26.6.105 · sail/tointeger-rounds)
- **`trim()` strips spaces but NOT newlines.** (m ≤26.6.105 · sail/trim-keeps-newlines)
- **`search()` cannot test substring presence** — `len(substitute(haystack, needle, "")) < len(haystack)` is the working form. (m ≤26.6.105 · sail/substring-test-via-substitute)
- **`text(-130, "0")` prints `13-0`** — route signed counts through `abs()` plus a word. (m ≤26.6.105 · sail/text-misplaces-sign)
- **`text()` NEITHER ROUNDS NOR GROUPS BEYOND WHAT YOU SPELLED OUT — it truncates, and it emits `N/A` when a number outgrows the format.** Two measured failures of the same function, both producing plausible-looking output: (1) `text(1.87005, "0.0")` returns **`"1.8"`**, not `"1.9"` — `text()` TRUNCATES to the format's precision, so `round()` to the target precision BEFORE `text()`, always; (2) `text(18700500, "#,##0.00")` returns **`"18700,500.00"`** — only as many thousands-separator groups as are LITERALLY written in the format are applied, and once the number outgrows them the call returns the string **`"N/A"`** (`text(2340000000, "#,###,##0.00")`). Write one group per magnitude you intend to support, one wider than the data's maximum. Same family as the `13-0` entry above: `text()` accepts the number and misreports it. (m ≤26.6.105 · sail/text-truncates-and-na)
- **Carry the real Date for arithmetic and the formatted string for display, never one value for both** — `todate("…")` vs a real Date silently never matches; `text(<Date as text>, "yyyy-mm-dd")` returns an error STRING without erroring. Clock basis is probed per instance. (m ≤26.6.105 · sail/date-value-vs-display-string)

### Lists, empties, joins, ordering
- **`wherecontains()` against an EMPTY list THROWS** — guard every filter on a non-empty source. `a!forEach` over an empty list returns Any Type, which `wherecontains` rejects. (m ≤26.6.105 · sail/wherecontains-empty-throws)
- **`index(list, <list of matches>, default)` returns ROWS; indexing a cell afterwards silently reads the wrong dimension** — wrap each row in `a!map(...)`. (m ≤26.6.105 · sail/index-returns-rows)
- **Two representations of an absent Document; `a!isNullOrEmpty()` catches one** — `index()` on an empty typed Document list returns `-2147483648`, passing the null check and failing downstream. (m ≤26.6.105 · sail/absent-document-min-int)
- **`union()` is not an ordering primitive** — iterate a canonical sequence and drop empties, or sort explicitly. (m ≤26.6.105 · sail/union-not-ordered)
- **Every join from a local list to a grid row needs `a!defaultValue(...)` with DISTINCT sentinels on both sides** (e.g. `-1` / `-2`) — a bare equality errors on Null vs Integer. Recurs on every screen filtering an assembled list per row. (m ≤26.6.105 · sail/join-sentinels-both-sides)
- **Write every nullable comparison/aggregate null-safe** so screens render under any data state. (m ≤26.6.105 · sail/null-safe-comparisons)

### Forms and state
- **In a multi-step form, NEVER save a list of Text** — `a!save(local!list, append(local!list, <text>))` destroys the form instance (back to step 1, all locals lost, no error). Hold state as a delimited scalar and derive: `local!xCsv: ";"` saved, `local!x: reject(a!isNullOrEmpty, split(a!defaultValue(local!xCsv, ";"), ";"))`, delimiters at both ends, never key from free text that could contain the delimiter. Appending a MAP to a list is fine. Empirical; root cause unknown. (m ≤26.6.105 · sail/text-list-save-destroys-form)
- **An interface with UNUSED LOCALS is REJECTED** — a hidden `showWhen: false` field referencing them satisfies the compiler. (m ≤26.6.105 · createInterface/unused-locals-rejected)

### Multi-record-type payloads (write-destroying trap)
- **`append()` onto a strongly typed record list SILENTLY DROPS rows of a different record type** — no error, `onSuccess` fires, the write does less than it claims. **`a!flatten({listA, listB, listC})` is the ONLY safe accumulator for a multi-record-type payload.** (m ≤26.6.105 · sail/append-drops-other-record-type)
- **A brace list is Any Type only if its members DIFFER.** A single-element brace list `{ 'recordType!X'(...) }` is homogeneous, types itself `List of X`, and is exactly as lethal as a typed `a!forEach` while looking safe. (This cost a build every launch it performed: nested appends onto a single-record brace list `{ parentRow }` silently discarded every child row.) (m ≤26.6.105 · sail/single-element-brace-list-is-typed)
- **A write path is verified ONLY by exercising the actual control and counting persisted rows per record type.** Direct payload inserts validate shape and bypass the control's accumulator; reading the expression, a green save, clean `testInterface`, and a successful direct insert are all non-verification. (m ≤26.6.105 · method/verify-write-by-control)

## 5. Row-level security: reads, keys, and diagnosis (ABSOLUTE)

- **Every readback in a row-secured app must state the account scope it ran under, or it can prove the wrong thing.** Record-level security filters `listRecordData`, `a!queryRecordType`, `.totalCount`, and every derived count — silently, with no marker distinguishing "absent" from "invisible to you". (This once diagnosed a complete seed as half-loaded, raised a Blocking TODO and proposed a reload — all artifacts of the reading account's scope membership.) (m ≤26.6.105 · records/readback-states-scope)
  - Write the scope into the readback itself ("as <user>, member of <groups>"), never just the numbers.
  - Before concluding rows are ABSENT, re-read as a member of every scope, or prove absence another way (a PK insert that succeeds proves the id was free; an id gap does not prove deletion).
  - `min`/`max`/`count` over a secured record type are per-viewer, never a high-water mark.
  - Restore original memberships afterwards and say so.
- **NEVER allocate a primary or business key as `max(...)+1` over a row-secured record type.** The max is the max *you can see*; `a!writeRecords` UPDATES when the supplied key exists, so the collision is a **silent overwrite of another scope's data**, not an error. Let the source assign keys (AUTO_INCREMENT; omit the PK), take FKs from relationships, or mint from an unsecured type. (This overwrote another scope's seed row.) (m ≤26.6.105 · records/no-max-plus-one-keys)
- **Writes targeted by primary key succeed against rows the calling account cannot read; only reads are filtered.** Useful for restoring another scope's data; a trap if you assume invisible means absent. (m ≤26.6.105 · records/pk-writes-bypass-rls)
- **TWO MCP SERVERS FOR ONE PLATFORM CAN COEXIST UNDER A SINGLE TOOL NAMESPACE WITH DIFFERENT EXECUTING IDENTITIES, AND TOOL NAMES DO NOT ANNOUNCE THEIR SERVER.** Before trusting any scoped read or any process you start, establish which server a tool belongs to and which identity it executes as; a naming-convention split between tool families (e.g. camelCase-unprefixed vs snake_case with a product prefix) is the usual tell, and the client's server listing may show only one of them. Under a foreign identity the failure is silent and green: row-secured reads return **empty** while PK-targeted writes still **succeed**, so a process completes, reports no error, and has read nothing — and anything downstream that reasons over that empty read (an LLM especially) will confabulate rather than fail. Diagnose by running the same read through a tool from each family, and by a control on data known to exist. **Supersedes the assumption in this section that a session has ONE identity: it warns that reads are filtered, but not that the identity can vary PER TOOL within one namespace.** **The fix is naming by role — `appian` for the Dev MCP, `appian-runtime` for the runtime server — so the two can never share a namespace.** Renamed by role, the two loaded separately: 157 and 10 tools (`reference/toolchain.md` §2, sail evaluation S34). Both failure shapes of a shared name were observed on one machine. (m 26.6.95 · mcp/two-servers-one-namespace)
  - **The shadow:** the name carried only the runtime server's 10 tools, and the design tools were missing while its `ping` answered.
  - **The merge:** 167 tools under one prefix. It passes the design-tool check and is caught only by the tool naming style.
- **Never key demo assets to platform-assigned ids** — derived numbers change on relaunch; identify specimens by their properties. (m ≤26.6.105 · method/no-platform-id-keys)

(m ≤26.6.105 · process/gate-audit-write-on-success)
- **A Write Records node's `EventType` ACCEPTS AN EXPRESSION, so ONE node emits differently-typed, differently-worded events with `CaptureEvents` left TRUE.** Compute the type id and the detail in the script node before the write and pass both as expressions (`EventType: pv!eventTypeId`, `comment: pv!eventDetail`); the platform still writes the event row, so the primary key is never minted. - **Events can be written WITHOUT writing records** — construct rows in a script task, ordinary Write Records node, `CaptureEvents` FALSE, set user/timestamp/eventTypeId/automationTypeId explicitly. The route when the platform's own event row will not do (the entry above replaces this one's former claim to be the only way to vary wording from one node). Never mint the PK. (m ≤26.6.105 · process/events-without-records)
- **The event `comment` field is the only working per-event detail field from the node — and only where commenting is disabled app-wide.** The documented "add a field" promise is Designer-only: the added field never appears in the node schema over MCP (HTTP 400 on send). - **An event's detail sentence is COMPOSED AT WRITE TIME from values in hand, and frozen forever** — never derived at render time, never backfilled. The old value exists only before the write (a reader node goes BEFORE the write node); rendered views fall back to the event type's name for pre-sentence rows rather than reconstructing from current data. **The freeze extends to notes and every mutable field**: a note joins the sentence only when the after-value DIFFERS from the before-value. Compose with a fixed category vocabulary and fixed priority for the length budget, so the identifying half is never the trimmed half. (m ≤26.6.105 · method/event-sentence-frozen-at-write)
- **Audit coverage is defined by a WRITE-PATH CENSUS, not by adding events where they seem useful.** Enumerate every write path and classify: **business** (user changing data — logs), **maintenance** (seeders, bulk re-dating — NEVER logs), **pre-record** (before the record exists — nothing to log against). **Maintenance machinery logging is a correctness defect — it forges a trail of edits nobody made**; an audit trail is worth its worst row. (m ≤26.6.105 · method/audit-by-write-path-census)

## 7. Column widths and schema changes (ABSOLUTE)

- **CREATING a column applies `length`. ALTERING one does NOTHING, silently, and every readback lies about it.** `addRecordTypeField(length: n)` produces a real VARCHAR(n). `updateRecordTypeField(length: n, updateTable: true)` returns 200, bumps the version, and leaves the physical column untouched — as do Designer type flips. `getRecordType` then reports the *requested* width, not the real one. **The only way to widen a column is DROP AND RECREATE.** (m ≤26.6.105 · updateRecordTypeField/length-alter-is-noop)
- **On CREATE the `length` is applied but BOTH record-type readbacks misreport it as 255 — narrower than the real column — so the add looks ignored when it worked.** `addRecordTypeField(fieldType: "TEXT", length: 4000, updateTable: true)` returned `sourceFieldType: "VARCHAR(255)"`, and a later `getRecordType` reported the same field as `VARCHAR(255)`, while `listDatabaseTableColumns` reported the physical column as **`VARCHAR(4000)`** and a subsequent write of a **364-character** value through a real Write Records node stored and read back the whole string. The same `getRecordType` call reported a pre-existing 4,000-character column correctly, so the metadata layer can report 4000 — it just does not for a field added this way, which makes it specific to the add rather than a blanket inability. The tool description says `length` "Set to 4000 to create a Long Text field" and says nothing about the reported type. **Why it is expensive in both directions:** believing the readback invites switching to `EXTRA_LONG_TEXT`, which spends one of only three such fields a record type may hold, carries usage restrictions and is refused by `a!eventData`; believing it the other way invites capping a truncation at 255 and silently clipping content (see the cap rule below, which requires the cap to EQUAL the measured column). **Working form:** settle a non-default `length` against `listDatabaseTableColumns` — read-only, zero residue, reads the physical schema — and, where the value matters, by writing a longer-than-255 value through the production write path and reading it back. Never from the add response or `getRecordType`. This narrows the entry above rather than contradicting it: CREATE does apply `length`; what also happens is that the readback understates it. (m 26.9.5 · addRecordTypeField/length-applied-but-misreported)
- **A width verification is valid only if the probe writes through the same path production uses** (for record apps: `a!writeRecords` via a Write Records node — throwaway process model, `PauseOnError: false`, errors mapped to PVs, driven by `testProcessModel`). Any historical width claim tracing to an ALTER is invalid until re-proven by write. (m ≤26.6.105 · method/width-proof-by-production-write)
- **A truncation cap in an expression must EQUAL the measured column** — below silently clips, above fails the write. (m ≤26.6.105 · sail/truncation-cap-equals-column)
- **Drop-recreate is surgery**: the new field gets a NEW UUID and the drop NULLS every row **including rows your account cannot see** (restore from the seed generator, not a readback). Repoint every reference by UUID — interfaces, rules, process nodes, **and record type user filters** (`sourceRef`, `relatedRecordDisplayField`; note `updateRecordTypeUserFilter` prepends the relationship UUID itself — pass the bare field UUID). Verify each by RENDERING it: **a dangling field UUID does NOT fail validation** — it saves clean and renders empty. (m ≤26.6.105 · records/drop-recreate-repoint-by-uuid)

## 9. Process models, writes, sites

- **A single Write Records node writing record types on DIFFERENT data-source handles fails as a SILENT TOTAL NO-OP** — process COMPLETED, `error: null`, zero rows written for EVERY type in the payload, including the ones whose handle was fine. `a!flatten` is the correct accumulator (§4) and does not rescue it. **One Write Records node per record type, chained; wire `ErrorOccurred`/`Error` on every business write; gate downstream nodes on write success.** Isolated by measurement: two record types sharing one handle write correctly from a single node, so the trigger is the handle split, not multi-type payloads. Contradicts the node schema's own "If writing multiple record types in Records, events can only be captured for one", which presents multi-type writes as generally supported. **`PauseOnError: false` with an unwired `ErrorOccurred` makes a failed write indistinguishable from a successful one** — the run still reports COMPLETED. (m ≤26.6.105 · process/one-write-node-per-handle)
- **Write Records' `RecordsUpdated` returns the generated primary key** (enables open-then-update), **but its ORDERING is not guaranteed — never join children positionally off it**; match on natural keys read back from the parent write. (m ≤26.6.105 · process/recordsupdated-order-not-guaranteed)
- **A WRITE RECORDS NODE HANDED AN EMPTY `Records` LIST ERRORS RATHER THAN NO-OPPING, SO AN OPTIONAL WRITE NEEDS A GATEWAY, NOT A CONDITIONAL PAYLOAD.** `Records: {}` fails the node with *The input "Records" must not be null or empty*; with `PauseOnError: false` the instance still completes, so the damage is not a stuck process but a **false error flag**: `ErrorOccurred` goes true and `Error` carries that text, and every downstream write-success gate reading those variables then blocks after a decision that was correct. Measured twice, on two models in two sessions: a rebuild node handed an empty restore list, and an optional flag-write whose payload rule correctly returned nothing for the majority of inputs (that one would have left the normal path reporting an error on 20 of 24 specimens). **Working form: put an XOR before the optional write whose condition asks the same question the write asks — is the payload rule's result non-empty? — with the default path straight to End.** Two evaluations of one deterministic rule over the same inputs cannot disagree, which is cheaper than a second implementation of the test; a guard inside the payload expression is NOT enough, because returning `{}` is exactly the case that errors. (m 26.9.5 · process/write-records-empty-list-errors)
- **A record-typed value inside an Any Type PV is LOST** (indexes Null; write rejects). Any PV carrying records through a map must be typed Map. (m ≤26.6.105 · process/record-in-any-type-pv-lost)
- **Only ONE smart service may run in an interface `saveInto`, and `onSuccess` accepts only `a!save()`/`a!httpResponse()`** — `a!writeRecords` cannot be chained inline to feed one write's key into the next. Multi-step writes: one call with nested related records (relationship must show `updateBehavior: "CASCADING"`) or a process model with chained nodes. The onSuccess variable is **`fv!recordsUpdated`**, not `fv!newRecords`. (m ≤26.6.105 · sail/one-smart-service-per-saveinto)
- **`a!startProcess` does not expose `fv!error` to `onError`** — only `a!writeRecords` does (the pack's contrary example fails validation). Write a self-contained failure message. (m ≤26.6.105 · sail/startprocess-no-fv-error)
- **No screen can be shown AFTER a related action's process finishes**; `testProcessModel` refuses models containing user input tasks. **That refusal does not arrive as a clean message**: measured, `testProcessModel` returns a bare `Network error:` (repeatably, on retry) and `appian_invoke_process_model` returns HTTP 500 `An unexpected error occurred` — even when the model has none of the Any Type parameters that tool separately rejects. Both read like infrastructure faults and will send you hunting; check the model for an attended node FIRST. A model with a user input task mid-flow is browser-only, end to end. Say what will happen on the start form. (m ≤26.6.105 · testProcessModel/attended-nodes-network-error)
- **Appian's AND gateway waits for ALL INCOMING CONNECTIONS, not all activated ones** — an AND join downstream of conditional branches deadlocks when a branch isn't taken. For "wait for all of N optional branches," route every branch to a single End node (a process stays active until every live flow ends). Reserve AND for the split. (m ≤26.6.105 · process/and-join-all-incoming)
- **Subprocess node inputs are PV NAME MAPPINGS, not expressions, and the API silently rewrites what you send**: `"myVar"` stores `pv!myVar`; `=pv!myVar` stores `pv!pv!myVar`; a literal stores NOTHING — all HTTP 200. Per-branch literals need their own PV with a default; computed values need a script node first. Always `getProcessModel` after writing a subprocess node and read every mapping back. (m ≤26.6.105 · createProcessModelNode/subprocess-inputs-are-pv-names)
- **AN ACP BOUND IN A USER INPUT TASK'S FORM `inputMap` IS FORCED `required: true`, AND BOTH `required: false` AND OMITTING THE FLAG ARE SILENTLY IGNORED ON SAVE** — the readback shows `true` either way, all HTTP 200. The consequence is a runtime failure with a distinctive message: an ACP fed from a process variable that is legitimately null on the happy path (an error-text PV populated only on failure, say) throws **`Missing required value for ac!<name>`** when the task is submitted, on every successful run. **The fix is never the flag; it is to guarantee a value** — wrap the source in `a!defaultValue(pv!x, "<non-empty literal>")`. Prefer a non-empty default: an empty string may still read as absent to the required check, and a form that already null-defaults the input renders the placeholder invisibly anyway. (m ≤26.6.105 · createProcessModelNode/form-acp-forced-required)
- **Script task (`internal.16`) outputs go in `data.customOutputs`, not `data.outputs`** (outputs is for schema-defined named outputs, e.g. ErrorOccurred/Error on Write Records). Contradicts the pack's `references/process-models.md` Script Task example, still `data.outputs` in the 26.6.105 bundle; the server's own `customOutputs` description agrees with this entry. (m 26.6.105 · createProcessModelNode/script-task-customoutputs)

(m 26.9.5 · listProcessModelNodeTypes/script-task-display-name)
- **A DESIGNER SAVE FROM A TAB OPENED BEFORE YOUR MCP WRITES PUTS THE WHOLE STALE MODEL BACK: LAST SAVE WINS, NO MERGE, NO WARNING.** A Designer tab holds the model as it was when the tab was opened. Saving it later writes that entire snapshot plus whatever was changed in the tab, silently reverting every MCP edit made in between. Measured on one process model: a tab opened at 18:15, two node expressions changed over MCP at 18:20 and read back, then a 20:45 Designer save that ADDED a process variable and dropped both expressions — confirmed by `listObjectVersions` plus a field-by-field diff of the last MCP-written version against the current draft, which showed exactly three differences (the new variable, the two reverted expressions, one cosmetic flow label). (m 26.9.5 · method/designer-tab-overwrites-mcp-edits)
- **`site!` page references need BOTH UUIDs** — `'site!{siteUuid}Name.pages.{pageUuid}page'`; Appian rewrites the trailing identifier on save, so never guess it: create pages, read the site back, take page UUIDs from the response. Prefer `a!urlForSite` (fails loudly at save) over hand-built Tempo URLs (404 silently at a user). (m ≤26.6.105 · sail/site-page-reference-both-uuids)
- **`updateSite` REGENERATES EVERY PAGE UUID and web address identifier, including untouched pages** — after ANY updateSite, read the site back and re-point every stored reference, then test the linking interface. (m ≤26.6.105 · updateSite/regenerates-page-uuids)
- **Site page schema exposes no navigation grouping over MCP; page groups are Interface-page-only anyway** — RECORD_LIST pages sit flat. Gate related pages with the same `visibilityExpr`; keep top-level items to eight (Appian's stated ceiling). **`visibilityExpr` hides the PAGE, not just the tab** — treat it as access control; links to hidden pages do not work. (m ≤26.6.105 · createSite/no-page-groups-over-mcp)
- **Configuring a record action does not surface it** — record views use `relatedActionShortcuts`; anywhere else place `a!recordActionField` deliberately; a grid's `recordActions` needs grid selection configured before `fv!identifier` works. (m ≤26.6.105 · sail/record-actions-placed-deliberately)
- **Send E-Mail (`internal3.sendemail3`) has four configuration traps, all of which fail late or silently.** (1) **`From` is a required non-nullable ACP** and is stored as a plain VALUE — `"Process Model"` — with an empty expression; omit it and the create fails with `Non-nullable input ACP(s) for unattended node(s) must not be null: From`. (2) **`IsHTML` must be TRUE for a body passed as text**: false switches the node to template mode and it then demands a `BodyTemplate` Document. Because the body is therefore rendered as HTML, separate lines with `<br>` and escape EVERY data value that reaches it. (m ≤26.6.105 · createProcessModelNode/send-email-four-traps)
- **MAIL AN APPIAN CLOUD INSTANCE SENDS IS STAMPED FROM THE SITE'S SYSTEM ADDRESS, WHATEVER THE NODE'S `From` SAYS — SO REPLIES ARE ROUTED BY `ReplyTo`, AND A LOOP TEST CAN NEVER BE AN AUTHORIZED SENDER.** Measured on one Cloud site (re-verify per instance): Send E-Mail with `From` = `"Custom Sender"` (a chosen address plus display name), `"Process Model"` and `"Process Designer"` all arrived at the same site's email-started process from `admin@<site>`; a live external reply from a mail client kept its real sender address and reached the receiver through the node's `ReplyTo`. Working form: (1) put the address replies must reach (e.g. the receiver's `processmodeluuid<uuid>@<site>` address) in **`ReplyTo`**, with the display name you want the thread to show; (2) when a flow authorizes replies by sender address, a loop test (the instance mailing its own receiver) exercises only the unauthorized path — test the authorized paths by temporarily mapping the roles under test to `admin@<site>` and restoring the mapping by readback afterwards, and prove the real-sender path with one live reply from a mail client. (three From modes by loop, repeated across two sessions, plus a live external control) (m 26.6.95 · process/mail-from-is-system-address)
- **"FAIL FORWARD ON ERROR" IS A PER-SMART-SERVICE NODE INPUT, NOT A NODE PROPERTY — AND IF THE SERVICE DOES NOT OFFER ONE, THERE IS NO WAY TO CATCH ITS EXCEPTION.** The pause-on-error switch is declared by each service and named differently every time: `Pause On Error` (Write Records), `Pause Node on Error` (Query Database), `Pause Node on HTTP Error` (Call Web Service). **Read the node type schema first**: if no such input is listed, the service has no fail-forward mode. **The Exceptions tab is NOT the fallback and does not catch errors** — the docs are explicit that all its events (Receive Message / Timer / Rule) are *evaluated before the activity executes* and that if one fires *the activity is not executed at all*. It pre-empts an activity; it cannot handle an activity that threw. (It is also not exposed over the Dev MCP: neither the node payload nor `updateProcessModelNode` has an exceptions field.) So when a plugin service throws, the flow at that node stops and never reaches ANY downstream gateway — a gateway placed after it can never run, because a gateway is downstream and the exception happened upstream. **The only fail-forward for such a node is not to run it**: gate it out, move it to a separate process instance whose failure is isolated, or remove it. Note also that per Process Errors an error on an UNATTENDED node does not set the process to Paused by Exception — the process keeps whatever parallel flows it has — so an instance stranded this way can look merely "still running" rather than failed. (m ≤26.6.105 · process/fail-forward-is-per-service)
- **A send/notify node placed AFTER a Write Records node cannot roll back or block that write.** The write has already committed and Appian does not undo a committed write because a later node errors; the worst case is a paused instance at the send node with the data change durable. This is the reason to attach notifications as new downstream nodes rather than as extra work inside the write node. (m ≤26.6.105 · process/post-write-nodes-cannot-rollback)
- **The Dev MCP process-model surface exposes no recurrence. Multiple node instances arrived in DevMCP 26.6.90 and are unmeasured at runtime.** (m 26.6.90 · createProcessModelNode/recurrence-and-mni)
  - **Recurrence.** `core.0` exposes no inputs and `updateProcessModel` has no recurrence field (`event.timer` is a DELAY timer, not a schedule). So a scheduled model is built complete and runnable over MCP, and its recurrence is set on the start event in Designer. Say so rather than reporting the model as finished.
  - **Multiple node instances.** The previous server generation had no MNI field. DevMCP 26.6.90 adds a `multipleInstance` block on `createProcessModelNode` and `updateProcessModelNode`, read from the server source, but no build has run one yet.
  - **Until that is measured, build a per-item fan-out (one email per case, one call per row) as the explicit loop that was measured working:** seed script (index and count) → XOR "any work?" → **take-item script** → work nodes → increment → XOR "another item?" → back to the take-item script. Every gateway then has exactly one incoming flow, and the continue condition carries a hard upper bound so a bad count cannot spin forever. **Never flow back into an XOR** — see the next entry.
  - **Next check:** the first time a build needs a per-item fan-out, try `multipleInstance` on a probe model. If it runs every item, it replaces the hand-built loop, and the XOR re-entry trap goes with it.
- **A FLOW RETURNING TO AN XOR GATEWAY THAT HAS ALREADY FIRED DOES NOT RE-ACTIVATE IT: THE INSTANCE SITS `ACTIVE` FOREVER, WITH NO ERROR AND NO PAUSED-BY-EXCEPTION.** Measured on an explicit loop built exactly as the entry above prescribed — seed → XOR(index ≤ count) → work → increment → back to the XOR. The first pass runs; the increment runs; the token then arrives at the gateway and nothing happens. The process is not paused, not errored, not completed: `testProcessModel` returns `status: "ACTIVE"` at timeout with the loop variables showing one completed pass (`idx: 2` against `count: 3`, trace `seed;take1=A;mid1;inc;`). **In production this reads as "the loop did one item and stopped"**, and because the instance never errors, the error-alert group is never notified and nothing in the audit trail says a run was abandoned. (m 26.6.95 · process/xor-reentry-hangs)
  - **Working form, measured on the same probe in the same session:** loop back to the **script node** that takes the item, and put the continue/stop XOR **downstream of the increment**, so every gateway has exactly ONE incoming flow. Seed → XOR(any work?) → **take-item script** → work → XOR(written?) → increment → XOR(another?) → back to the take-item script. That ran all three iterations and returned `COMPLETED` in 6.5 s, trace `seed;take1=A;mid1;inc;take2=B;mid2;inc;take3=C;mid3;`.
  - **A script node re-entered by a loop-back fires every time** — only the gateway does not. Multiple incoming flows on a script node are fine.
  - **Isolate this before blaming the work nodes.** The same loop with Start Process nodes in it hung identically, which reads like a smart-service fault; removing them and re-running proved the smart services were never involved. A loop that stops after one pass is a gateway-re-entry suspect first.
  - **Contradicts** the explicit-loop recipe in the entry above (now corrected), which is also how Appian loops are commonly drawn.
- **Verification ceremony scope**: these are build-time and change-time rules. Routine operation of a working build (deleting a practice case, relaunching, running a demo) needs no readback, no row count, no wrapper — build-time rigor, run-time simplicity, and ceremony retires with the defect it was built for. (m ≤26.6.105 · method/ceremony-scope)
- **A NODE WITH NO INCOMING FLOW IS NOT INERT: IT EXECUTES WHEN THE PROCESS STARTS.** Measured on two node types in one session, on the same model, over dozens of runs. An XOR gateway created ahead of the flow that would eventually reach it — waiting on one Designer edit — fired at process start on **every** run, before the write node that fills the variables it reads; its conditions saw empty process variables, it took its default path, and the write node on that path received a record value with a **null primary key**, which is an insert. Twenty-four intake runs left twenty-four phantom rows, each with its related child, in a record type shared with the demo's own data. Separately, an **Execute AI Agent** node left unconnected for three runs fired at start the same way and **invoked the model on empty context**, consuming AI actions, with the context-resolved gate in front of it bypassed entirely because the flow never came through it. Nothing in either case raised an error: the runs returned `COMPLETED`, and the phantom rows were found only by a count readback against an expected total. **Why it is easy to walk into:** `createProcessModelNode` accepts a node with no incoming flow (it has to — `connections` are outgoing only, so a node is always created before the flow into it exists), and the tool's own text says only that an **End** event needs an incoming flow to be publishable, which reads as though an unconnected activity node simply never runs. **Working form: a half-built branch must be inert BY ITS OWN CONDITIONS, never by being unreachable.** Put a context test first on the gateway that heads it — "is there anything in hand to act on" — with the default path going straight to End writing nothing, and guard the payload rules too: a rule that builds a record value must refuse a null primary key and return `{}` rather than a value, so the worst case is an empty write the error output reports instead of a silent insert. Then re-count per record type after the first run. (m 26.9.5 · createProcessModelNode/unconnected-node-runs-at-start)

## 10. Layout and component facts

- **`a!sideBySideLayout` REJECTS a card as an item** — use `a!cardGroupLayout`. (m ≤26.6.105 · sail/sidebyside-rejects-card)
- **A ROW OF CARDS IS LEVELLED BY THE GROUP, NEVER BY THE CARDS.** `a!cardLayout(height: "AUTO")` sizes EACH card to ITS OWN contents, so a row of cards with different body lengths — laid out as `a!columnsLayout` of `a!columnLayout`s, the obvious shape — ends ragged, and the tempting fix (pin every card to one fixed height token) trades ragged for either a crater of empty space or silently scrolling content. `a!cardGroupLayout` is documented as displaying "an arrangement of cards, with the same width and height", and ITS `cardHeight: "AUTO"` means every card takes the height of the TALLEST. Same keyword, opposite meaning, depending on which component owns it. Pass the cards DIRECTLY as `cards:` with no column wrapper; `cardWidth` is a FLOOR that `fillContainer: true` expands from, so pick a narrow token for a fixed small number of cards and let them fill. This is the second reason to reach for a card group, independent of the side-by-side rejection above. (m ≤26.6.105 · sail/cardgroup-levels-heights)
- **FILLER IS A PIN YOU CANNOT GREP FOR.** Removing a `height` token and replacing it with margin/padding that reaches the same height is the SAME decision with the audit trail deleted. Measured over three versions of one card: pinned to a height token; "unpinned" by adding ~274px of enumerated margin to its rows to reach the same edge as its neighbour; reported as sprawl the moment its content grew by one row. A height pin at least announces itself to the next reader and to `grep`; spacing that exists to hit a neighbour's edge looks like typography and is found only by someone counting tokens against a comment. **Working form: a container's height is an OUTPUT of its content. When two neighbours must end level, that is the job of the component that levels them — `a!cardGroupLayout`, whose `cardHeight: "AUTO"` gives every card the height of the tallest — never of per-child spacing.** (m ≤26.6.105 · sail/filler-is-a-hidden-pin)
- **A FIXED-WIDTH GRID COLUMN IS SIZED BY ITS WIDEST *WORD*, HEADER INCLUDED, AND `NARROW` HAS NO FLOOR** — so a column whose VALUES are short will break its own HEADER. Measured: an eight-character label over two- and three-digit values in a `NARROW` column rendered as "Duratio" over "n". The docs state both halves separately — a fixed-width column "will be at least as wide as the longest word in the column", and "`ICON` and `NARROW` do not have a minimum width" — but never draw the consequence: **the header is one of the words being measured, and in a numeric column it is usually the longest one.** Working form: **size a narrow numeric column by its LABEL, not its values.** Where the label is the long part, SHORTEN THE LABEL and put the full term in `helpTooltip`, rather than widening — widening spends width that the `AUTO` columns beside it need (see the entry below: what a fixed column takes, an AUTO column loses). (m ≤26.6.105 · sail/narrow-column-sized-by-label)
- **`AUTO` width means "whatever the fixed columns leave"** — it belongs to the column that tolerates any width; freed pixels go to the AUTO column, so a remedy naming the wrong column is worse than none. (m ≤26.6.105 · sail/auto-width-takes-remainder)
- **`shadeAlternateRows` defaults true**; where shading and a STANDARD divider compete, weaken the divider (`borderStyle: "LIGHT"`). (m ≤26.6.105 · sail/shade-vs-divider)
- **A constrained `size` on `a!imageField` serves a RESIZED rendering — a resized animated GIF is one flattened frame.** Only `size: "FIT"` serves the file unresampled. (m ≤26.6.105 · sail/image-size-fit-for-gif)
- **`helpTooltip`'s icon does not show with COLLAPSED label position**; `a!richTextDisplayField.tooltip` has no such restriction. (m ≤26.6.105 · sail/helptooltip-collapsed-label)
- **SAIL cannot restyle an input on focus** — CSS profiles are Admin Console, site-level, no focus state in the published property list, applied to every input at once. (m ≤26.6.105 · sail/no-focus-styling)
- **Alignment vocabulary is per-component and not interchangeable**: rich text takes `LEFT`/`CENTER`/`RIGHT`; grid columns and button arrays take `START`/`END`; `a!tagField` has no `align` at all. (m ≤26.6.105 · sail/align-vocabulary-per-component)
- **`a!kpiField` takes `align`, NOT `labelPosition`** — the pack's labelPosition examples are rich-text-in-cards, not KPI fields; never carry parameters across patterns. (m ≤26.6.105 · sail/kpifield-align-not-labelposition)
- **`a!recordActionField` takes `style: "LINKS"` (plural) and has NO `labelPosition`.** (m ≤26.6.105 · sail/recordactionfield-style-links)
- **`addRecordTypeView.nameExpression` wants `="Summary"`** — the `='"Summary"'` form the tool's own parameter description gives (`='"My View"'`, in `addRecordTypeView` and `updateRecordTypeView` through 26.6.105) fails as an unresolved reference. The pack carries no such form. (m 26.6.105 · addRecordTypeView/name-expression-form)
- **Platform deltas never to fight when matching mockups**: no per-interface fonts (rich text size/weight for hierarchy; never font workarounds); no segmented progress component (colored glyphs or per-segment cards); no expandable/spanning rows and no row grouping in `a!gridField` (grouped reading = sectioned layout; flagged-items card section replaces expanded rows); no sticky footers, custom hover states, or exact pixel spacing. Page/header chrome comes from site-level branding — never build a brand bar inside an interface. (m ≤26.6.105 · sail/platform-deltas-not-fought)
- **Chat components**: `a!recordsChatField` is native per-record chat on a record summary view, cloud-only, requires site enablement — verify on the target environment before assuming. No native cross-record chat: build with `a!chatField()` backed by an agent or `a!callLanguageModel` over Data Fabric queries; suggestion chips are buttons submitting preset prompts. Chat answers vary across runs (documented) — fallback screenshots for every chat beat are mandatory prep. (m ≤26.6.105 · sail/chat-components)
- **Idioms that consistently work**: `a!kpiField` or KPI-in-a-card, risk metrics first; statuses as colored `a!tagField` via `a!match`, never raw text; identifiers as `a!recordLink`, never plain strings; reference-data dropdowns from live records, never hardcoded. (m ≤26.6.105 · sail/working-idioms)

## 11. AI agents (platform)

- **An Agent Studio record-data tool returns the backing record type's OWN fields only — no relationship traversal.** The Record Fields panel on the tool is **display-only, showing what comes back; it is not a picker** and cannot be extended to related types. Related context therefore costs either **one tool per record type (a query per type per run)** or **process-side assembly into a single text input** — prefer the latter for latency, deterministic wording, and because the query then runs in the process's security context rather than the agent identity's. **Why this is slow to diagnose:** the tool does not error; related fields are simply absent, which is byte-identical to an omitted `fields:` list (§4) and to a row-security filter (§5/§7). Symptom to recognise: the agent's own output says the context lacked the related data, and confidence collapses. (m ≤26.6.105 · agents/record-tool-no-traversal)
- **The documented default document tool is Semantic Search, not Read Full Document** — an instruction to read fully is load-bearing. Read Full Document ceilings: 50 pages text-only, 20 with images; per-run budget 75 documents / 50 MB. (m ≤26.6.105 · agents/read-full-document-is-opt-in)
- **Whether an agent iterates every element of a Document array is agent reasoning, not a platform guarantee** — say so explicitly in instructions and test with a distinctive requirement planted in the second document. (m ≤26.6.105 · agents/array-iteration-not-guaranteed)
- **AN AGENT OUTPUT DECLARED AS AN ARRAY READS BACK AS PLAIN `Text` WITH NO MULTIPLE FLAG, AND BEHAVES AS A LIST ANYWAY.** Measured across two sessions on one Execute AI Agent node: `getProcessModelNode` reported the agent's one array-declared output ACP as type `Text`, exactly like its eleven single-valued siblings, while at runtime the same output returned an empty list on one run and **four- and five-item lists on others**, all landing intact in a `Text` **multiple** process variable. The readback is therefore not a type declaration for multiplicity — and the absence reads as a positive statement, because `multiple` *is* reported on process variables and on record fields, so a session sizing a downstream variable from this readback would make it single-valued and silently keep one item of a list. **Working form: take an agent output's multiplicity from the agent's own build sheet, declare the receiving process variable multiple, and confirm it by a run that returns more than one item** — a two-item list landing intact is the proof; the readback never will be. (m 26.9.5 · getProcessModelNode/agent-output-multiplicity-absent)

- **AN EXECUTE AI AGENT NODE IS CREATABLE AND DRIVABLE OVER THE DEV MCP, ITS INPUT IS MAPPABLE BY CONVENTION, AND ITS DECLARED OUTPUTS ARE UNREACHABLE — SO THE RUN COMES BACK GREEN WITH NOTHING EXTRACTED.** Measured on `internal3.execute_ai_agent_v2`, DevMCP 26.9.5 build `20261026-140102`, across four node writes and four live runs on one node.
  - **The create works bound.** `createProcessModelNode` with `data.inputs: [{name: "AgentUuid", value: "<uuid>"}]` is accepted; take the UUID from `listAgents(appUuid)`. Unbound is still refused — `AgentUuid` is a non-nullable ACP — so "add it now, bind it later" is not expressible. **This supersedes any claim that the node cannot be created over MCP at all.**
  - **The input is a custom ACP named `_agentInput_` + the agent's declared input name**, carried in `data.customInputs` with an `expression`. The prefix is the one the node-type schema documents (`AgentInputs` is a "Legacy input map. Dynamic `_agentInput_` ACPs are used instead in V2"). It genuinely reaches the model: a run's `Run Summary` quoted facts present only inside the text passed on that ACP.
  - **There is no symmetric output convention.** `data.outputs` with a declared output name → HTTP 400 `Unknown output '<name>' — use customOutputs for custom ACPs`. `data.customOutputs` with `=ac!<name>` → accepted on write, then fails the run: `Could not find variable 'ac!<name>' (Data Outputs)`. `=ac!_agentOutput_<name>` fails identically, probed on two different output names so a name-specific failure could not pass for a convention failure. A `customOutputs` entry is an expression-to-PV pair with **no name** (the pack's `references/process-models.md` says so), so nothing in this API can *declare* an output ACP. **Working form: one Designer edit — open the node, re-pick the agent in the Setup tab, save — then read the generated names off the node.**
  - **Why it is dangerous rather than merely limited:** with no output wired the run **completes**, `Success` is true, AI actions are consumed, and `Run Summary` states that every declared output was set, while every process variable stays null. The loud failure only appears if you wire an output and it cannot resolve. A session that maps nothing concludes the agent did nothing wrong.
  - **`AgentUuid` is not validated against an existing agent on write.** A UUID mistyped into one hex group was stored and read back without an error or a warning; only comparing the readback against `listAgents` caught it. A run under a non-existent agent was not attempted. Treat `AgentUuid` like any other never-invent-a-UUID field and verify the stored value character by character.
  - **THE PICK IS WHAT CREATES THE ACPs, AND AFTER IT THE NODE'S DATA TAB IS DESIGNER-ONLY.** Measured across all three states of one node in one session. **Before the pick:** the node has no agent ACPs at all, and a declared input missing from the readback means the pick has not happened — it never means an ACP must be invented. **After one Designer pick:** the ACPs appear as ordinary named entries, inputs under `inputs` and outputs under `outputs`, named `_agentInput_<declaredName>` and `_agentOutput_<declaredName>` with the agent's declared types. **But they are not settable over MCP, and worse, any `data` write destroys them.** `data.inputs` with `_agentInput_message` → HTTP 400 `Unknown input '_agentInput_message' — use customInputs for custom ACPs`; `data.outputs` with `_agentOutput_caseType` → `Unknown output '_agentOutput_caseType' — use customOutputs for custom ACPs`. Both lists validate against the **static** node-type schema, which never lists them. And since `data` is a full replacement, a write that cannot carry them **deletes them**: after one `updateProcessModelNode` sending the five built-in outputs plus twelve `customOutputs`, a fresh `getProcessModelNode` showed the twelve declared ACPs gone, the next run failed on `Could not find variable 'ac!_agentOutput_caseType'`, and **nothing in the API can write them back** — only another Designer pick restores them. **Working form: after the pick, set the agent input's expression AND map every agent output to its process variable in Designer, and never send a `data` block to that node again.** A `customInput` named `_agentInput_<name>` does feed the model (proven by a run), so the input alone can be done over MCP; the outputs cannot be, at all.
  - **A failed Data Outputs phase leaves typed zeros, not nulls.** When the output evaluation threw, the run's variables came back `exAmount: 0.0`, `exConfidence: 0.0`, `exRunId: 0`, `exAiActions: 0`, `exMissingFacts: {}` — and `null` on the Text ones. So a downstream check must not read `confidence = 0.0` as a model reading; distinguish "the node failed" from "the model answered zero" on `Success` and `ErrorMessage`, never on a value.
  - (m 26.9.5 · agents/node-outputs-unreachable-over-mcp)

## 12. Working practices (portable method)

- **Naming pattern** (each project sets its prefix; the pattern is constant): record types `<PREFIX> <Entity>` singular; interfaces `<PREFIX>_<context><Purpose>` camelCase; rules/constants `<PREFIX>_<purpose>`/`<PREFIX>_<PURPOSE>`; groups `<PREFIX> <Scope>`, runtime groups under `<PREFIX> Users`. (m ≤26.6.105 · method/naming-pattern)
- **Security baseline**: never `All Users` viewer on business data; Administrators (design) segregated from runtime groups; row-level scoping defined ONCE on the anchor record type(s), inherited everywhere via RELATED_RECORDS — never per-interface filtering, never restated conditions; no credentials or secrets in SAIL or sample data. (m ≤26.6.105 · method/security-baseline)
- **Data fabric purity for data-fabric demos**: 100% record types — never a CDT, never a data store entity, not even to satisfy a smart service that wants one (e.g. Export DSE to Excel is off the table; enumerate record-native alternatives). One stray CDT in the object list undercuts the demo's own argument and is what a technical reviewer looks for. (m ≤26.6.105 · method/record-types-only)
- **Deterministic sample data**: static values, no `rand()`/`now()`/`today()` in seeds — identical across re-evaluation. Regenerate by script, never hand-edit rows; any scripted duplicate of an in-app rule stays behaviorally identical to it. (m ≤26.6.105 · method/deterministic-seeds)
- **Shared logic implemented ONCE** as a single expression rule used by every consumer, with variation as a parameter — never duplicated inline, never a second rule. (m ≤26.6.105 · method/shared-logic-once)
- **Structural rule**: 360s are record types with views and related actions, not bespoke interfaces; portfolio/list pages are site pages backed by the record type. (m ≤26.6.105 · method/360s-are-record-types)
- **Two presentations of hierarchical data, distinct jobs, never mixed**: flat sortable/filterable grid (repeated parent values down columns are correct — they power filtering and export) and a grouped sectioned reading view. (m ≤26.6.105 · method/flat-grid-vs-grouped-view)
- **Legacy → modern transform order** (verify each): headerContentLayout + brand header; KPI row of the domain's risk metrics; FK numbers → relationship traversal; plain-text status → colored tags + date-risk coloring; identifiers → recordLink; re-validate to `diagnostics.error: null`. (m ≤26.6.105 · method/modernisation-order)
- **Agent-generated objects are drafts pending human review**; field-setting documented with `TODO-CONVERTER:` comments, side-effects with `TODO:`. (m ≤26.6.105 · method/generated-objects-are-drafts)
- **Live over fixtures**: rehearsals and click tests run the real agent path; assertions target the live run, never fixture recordings. Fixtures are break-glass for a failed demo-morning check, nothing else. (m ≤26.6.105 · method/live-over-fixtures)
